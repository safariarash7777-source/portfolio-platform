## ۹) تصحیحِ تحلیلِ خودم — `raw` افزونه نیست، تنها خانهٔ OHLC است

مسیرِ اشتباهی که رفتم و اصلاحش: نمونهٔ یک `raw` از `brsapi_candle` این است

```json
{"low": 30001, "high": 30501, "open": 30001, "time": null, "jdate": "1395-04-12", "candle": true}
```

و چون ستون‌های تایپ‌دارِ `low/high/open` هم وجود دارند، در نگاهِ اول «تکرارِ
همان داده» به‌نظر می‌رسید و نامزدِ ۲۵۳ مگابایتیِ حذف شد. سنجش خلافش را گفت:

| بررسی روی ۱٬۹۴۱٬۰۹۷ ردیفِ `brsapi_candle` | نتیجه |
|---|---|
| `low` ستونی NULL | **۱٬۹۴۱٬۰۹۷ (۱۰۰٪)** |
| `high` ستونی NULL | **۱۰۰٪** |
| `open` ستونی NULL | **۱۰۰٪** |
| `close` ستونی NULL | ۰ |
| `raw->>'low'` NULL | ۰ |

پس **Open/High/Low برای کلِ ۲۵ سال فقط داخلِ `raw` زندگی می‌کند**؛ ستون‌هایش
هرگز پر نشده‌اند. پاک‌کردنِ `raw` نمودارِ شمعی، دامنهٔ روز، ATR و هر بک‌تستِ
مبتنی بر OHLC را نابود می‌کرد — و **بی‌صدا**، چون ستون از قبل NULL است و
مصرف‌کننده فرقی نمی‌دید.

اقدامِ درست حذف نیست، **نرمال‌سازی** است: انتقالِ `raw.low/high/open` به همان
سه ستونِ تایپ‌دار و سپس دورانداختنِ jsonb. تخمین: ۲۲۰ MB آزاد، ~۵۸ MB برای سه
`numeric` اضافه ⇒ **خالص ≈۱۶۲ MB**، و برای اولین بار OHLC در SQL قابلِ
پرس‌وجو می‌شود. این یک migration است و پشتِ گیتِ مالک می‌ماند.

## ۱۰) تصحیحِ نرخِ رشد — «۱۳۹ MB/سال» غلط بود

عددِ قبلی را با **روزهای تقویمی** حساب کرده بودم (۳۸۰ kB × ۳۶۵). رله فقط
روزهای معاملاتی می‌نویسد (شنبه–چهارشنبه، `pushDailyHistory`). اندازه‌گیری:

| سنجه | مقدار |
|---|---|
| روزهای معاملاتی در ۳۶۵ روزِ گذشته | **۲۴۱** |
| میانگینِ ۳ساله | ۲۳۹ روز در سال |
| ردیفِ ثبت‌شده در ۳۶۵ روزِ گذشته | ۱۹۳٬۳۹۱ |
| نرخِ اخیر (نمونهٔ ۲۱ روزه) | ≈۱٬۰۳۰ ردیف در هر روزِ معاملاتی |
| بایت به ازای هر ردیف، امروز | ۷۴۲ MB ÷ ۲٬۰۹۵٬۱۱۹ = **۳۷۱ B** |
| بایت به ازای هر ردیف، پس از حذفِ دو index | (۷۴۲−۱۲۵) ÷ ۲٬۰۹۵٬۱۱۹ = **۲۹۴ B** |

⇒ رشدِ سالانه پس از پاک‌سازیِ index: **۵۷ MB** (نرخِ سالِ گذشته) تا
**۷۲ MB** (نرخِ اخیر). برای برنامه‌ریزیِ ظرفیت، محافظه‌کارانه **۷۲ MB/سال**
= ۶ MB در ماه گرفته می‌شود.
