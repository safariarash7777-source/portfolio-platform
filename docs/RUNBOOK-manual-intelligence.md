## ۰) قاعدهٔ سختی که همه‌چیز بر آن تکیه دارد

**`تأییدشدهٔ داخلی` با `منتشرشده` یکی نیست.**

آرش می‌تواند یک تحلیل را برای استفادهٔ داخلی تأیید کند بدون اینکه ذره‌ای از آن
جلوی مشتری برود. این تفکیک در **سه جای مستقل** نگه داشته می‌شود، چون یک جا
نقطهٔ شکستِ واحد است:

| لایه | چه چیزی را تضمین می‌کند |
|---|---|
| قیدِ `intel_analyses_publication_consistent` | `approved_internal` باید `published_at = NULL` داشته باشد |
| تریگرِ `intel_guard_analysis_mutation` | `published` فقط از `approved_internal` قابلِ رسیدن است |
| سیاستِ `intel_public_read_published` | دستِ‌نخورده روی `status = 'published'` — نسبت به هر دو حالتِ تازه کور است |

`lib/intelligence/workflow.test.ts` هر سه را **جداگانه** می‌سنجد، و
`lib/intelligence/service.test.ts` ثابت می‌کند مسیرِ API هم مقصدِ `published` را
رد می‌کند حتی برای ادمین و حتی از حالتِ درست. **در این مأموریت هیچ دکمهٔ انتشارِ
عمومی ساخته نشده است.**

## ۱) گردشِ روزانه

```
رخداد
  → منبع و شاهد            (intel_sources + intel_evidence)
  → تحلیل و سناریو          (intel_analyses + intel_claims)
  → اثر بر سبد مرجع         (intel_portfolio_effects)
  → بازبینی انسانی          (pending_approval)
  → تأیید داخلی             (approved_internal)   ← پایانِ کار در این مأموریت
  → ثبت اصلاحات و سنجه‌ها     (intel_workflow_events + intel_rehearsal_days)
```

### گام‌ها در پنل

۱. **`/admin/intelligence` → امروز.** اگر بریفی برای امروز ثبت نشده باشد،
   صفحه صریح می‌گوید «ثبت‌نشده» — نه «۰ گزاره». این دو یکی نیستند.

۲. **ثبتِ بسته.** یک تماسِ `POST /api/admin/intelligence` کلِ بسته را می‌فرستد
   و `capture_intel_package` آن را در **یک تراکنش** می‌نویسد. اگر هر جزء رد
   شود، هیچ‌چیز نمی‌ماند — نه منبعِ بی‌صاحب، نه شاهدِ آویزان.

   هشِ محتوا **سمتِ سرور** ساخته می‌شود (`sha256` روی متنِ شاهد + نشانی + زمانِ
   مشاهده). کلاینت هرگز آن را تعیین نمی‌کند؛ اگر بفرستد، نادیده گرفته می‌شود.

۳. **ارسال برای بازبینی.** `draft → pending_approval`. از این لحظه **محتوا
   قفل است** — تحلیل زیر دستِ بازبین بازنویسی نمی‌شود.

۴. **صندوق بازبینی.** هر مورد پیش از فشردنِ دکمه می‌گوید آیا تأیید ممکن است و
   اگر نه، چرا: «۲ گزاره هنوز شاهد ندارد». دکمهٔ تأییدی که دیتابیس بعداً ردش
   کند، بدتر از نبودنِ دکمه است.

۵. **تأیید داخلی یا رد.** `approved_internal` نیاز به تأییدکننده، زمان، دستِ‌کم
   یک گزاره و شاهد برای **هر** گزاره دارد. `rejected` هر وقت ممکن است و تحلیل
   می‌تواند به پیش‌نویس برگردد.

   بازگرداندن به پیش‌نویس **امضای تأیید را پاک می‌کند**. وگرنه متنِ
   بازنویسی‌شده تأییدی را حمل می‌کرد که به متنِ قبلی داده شده بود.

۶. **ثبتِ روزِ تمرین.** `POST /api/admin/intelligence/rehearsal`.

## ۲) دفترِ گردش — تاریخچه‌ای که خودش را می‌نویسد

`intel_workflow_events` را **تریگر** پر می‌کند، نه اپلیکیشن. اگر یک روت فراموش
کند لاگ بزند — یا تصمیم بگیرد نزند — تاریخچه دقیقاً همان‌جا سوراخ می‌شود که
بیشترین اهمیت را دارد. اینجا گذار و ثبتش یک تراکنش‌اند.

**هیچ‌کس `UPDATE` روی این دفتر ندارد، حتی `service_role`.** حذف هم ممکن نیست.

| رویداد | چه زمانی |
|---|---|
| `captured` | ساختِ تحلیل |
| `submitted` | `→ pending_approval` |
| `approved_internal` | `→ approved_internal` |
| `rejected` | `→ rejected` |
| `returned_to_draft` | `→ draft` |
| `published` · `superseded` | فقط از مسیرِ جداگانهٔ انتشار (در این مأموریت ساخته نشده) |

## ۳) دفترِ تمرین

برای هر روزِ **واقعی** یک ردیف در `intel_rehearsal_days`:

تاریخ · شمارهٔ روز · آیا بریف تولید شد · زمانِ کل تا تأیید · منابعِ غایب ·
منابعِ بیات · تعدادِ اصلاحِ انسانی · نتیجه‌گیری‌های ردشده · رخدادهای ازدست‌رفته ·
یادداشتِ پیگیری.

منابعِ غایب و بیات **نام** ذخیره می‌شوند نه شمارش: «سه منبع بیات بود» قابلِ
پیگیری نیست، «این سه منبع بیات بودند» هست.

### قواعدِ سختِ دفتر

- روزی که بریف نداشته **نمی‌تواند** زمانِ تولید یا ارجاع به بریف داشته باشد.
  بدونِ این قید، «امروز بریف نداشتیم» و «بریف در صفر دقیقه آماده شد» یک ردیف
  می‌شدند.
- روز تا وقتی **مهر نشده** قابلِ اصلاح است؛ سنجه‌ای که یک ساعت بعد فهمیده شود
  هنوز سنجهٔ واقعی است. پس از `seal_rehearsal_day` منجمد می‌شود.
- تاریخ و شمارهٔ روز **هرگز** تغییر نمی‌کنند — همان چیزی که ده روز را شمردنی
  می‌کند.
- **حذف وجود ندارد**، برای هیچ نقشی.
- هیچ روزِ مصنوعی، backfill یا نمونه‌ای در هیچ migration یا مسیری ساخته
  نمی‌شود. تستِ `no seed, sample or bootstrap rehearsal day ships in the
  migration` همین را قفل می‌کند و **شکست‌پذیری‌اش اثبات شده**.

### گزارشِ تجمیعی

`summarizeRehearsal` **`null` برمی‌گرداند، نه صفر**، وقتی چیزی اندازه‌گیری
نشده. یک تمرینِ شروع‌نشده نباید شبیهِ ده روزِ کاملاً ناموفق به‌نظر برسد.

| وضعیت | معنا |
|---|---|
| `not_started` | هیچ روزی ثبت نشده |
| `in_progress` | کمتر از ده روزِ واقعی |
| `ready_for_review` | ده روزِ واقعی ثبت شده — **و این PASS نیست** |

**`ready_for_review` هرگز `PASS` نیست.** تصمیمِ Gate 3 با Command Center است.

## ۴) شروعِ تمرینِ ده‌روزه

**تمرین هنوز شروع نشده و این runbook آن را شروع نمی‌کند.**

پیش‌نیازها، هیچ‌کدام هنوز برقرار نیست:

- [ ] PR-B و PR-C بازبینی و merge شده باشند
- [ ] Command Center شروعِ رسمی را تأیید کند
- [ ] روزِ صفر و baseline ثبت شود (اولین ردیفِ واقعی، بدونِ روزِ ساختگی)
- [ ] محیطی که تمرین روی آن اجرا می‌شود مشخص باشد — **Preview متصل به Staging
      هنوز تأیید نشده** (بلاکرِ اتصالِ Vercel، `B-031`)

روزِ ازدست‌رفته **جعل نمی‌شود**. اگر روزی بریف تولید نشد، همان‌طور ثبت می‌شود:
`brief_produced = false`. تمرینی که روزهای بدش را پنهان کند چیزی نمی‌سنجد.
