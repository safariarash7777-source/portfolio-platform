## گام ۱ — اجرای migration روی **staging**

فایل: [`sql/phase8b_leads.sql`](../sql/phase8b_leads.sql)

خواصِ راستی‌آزمایی‌شدهٔ فایل (فقط‌خواندنی، بدونِ اجرا):

| خاصیت | شاهد |
|---|---|
| idempotent | `CREATE TABLE IF NOT EXISTS` · `DROP POLICY IF EXISTS` · `CREATE INDEX IF NOT EXISTS` |
| غیرمخرب | هیچ `DROP TABLE`، هیچ `DROP COLUMN`، هیچ تغییرِ نامِ شیٔ دیگر |
| RLS | `ENABLE ROW LEVEL SECURITY` + سیاستِ `service_role` + سیاستِ `admin` |
| قفلِ anon | `REVOKE ALL ON public.leads FROM anon` |
| اعتبارسنجی | `CHECK` روی `status` و طولِ `name` |
| ایندکس | `created_at DESC` · `status` · `(phone, created_at)` · `telegram_id` |
| rollback | بلوکِ صریح در انتهای فایل |

**dedup عمداً UNIQUE ندارد** — کامنتِ خودِ فایل: یک قیدِ یکتای دائمی، درخواستِ
مجددِ مشروعِ همان شخص را برای همیشه رد می‌کند. تشخیصِ تکرار در `lib/leads/webhook.ts`
با پنجرهٔ ۱۰ دقیقه‌ای انجام می‌شود.

```bash
# فقط روی پروژه/برنچِ staging — هرگز روی Production
# با ابزارِ انتخابی (Supabase SQL editor روی برنچِ staging یا CLI)
```

## گام ۲ — چک‌لیستِ شواهد

هر بند باید **خروجیِ واقعی** داشته باشد، نه فرض:

- [ ] `select relrowsecurity from pg_class where relname='leads';` → `true`

- [ ] ردیفِ MySQLِ محلی ساخته شد
- [ ] وبهوک **۲۰۰** برگرداند (نه ۴۰۱ — این همان چیزی است که `B-020` می‌شکست)
- [ ] ردیفِ متناظر در Supabase `leads` هست
- [ ] در پنلِ ادمین دیده می‌شود
- [ ] ارسالِ دوبارهٔ همان لید در پنجرهٔ ۱۰ دقیقه‌ای **تکراری** تشخیص داده شد
- [ ] `/admin/health` ردیفِ «آمادگیِ جدولِ لید» را `ok` نشان می‌دهد

## گام ۳ — رفتار با رکوردِ مصنوعی

طبقِ سیاستِ آزمونِ تأییدشده حذف یا نگه داشته می‌شود. **پیش‌فرض: حذف** —
`delete from public.leads where name like 'TEST\_%';` روی **staging**.
(جدول append-only نیست، پس حذفِ رکوردِ آزمایشی مانعِ سیاستی ندارد.)

## گام ۴ — rollback

بلوکِ انتهای `sql/phase8b_leads.sql`:

```sql
-- DROP TRIGGER  IF EXISTS trg_leads_set_updated_at ON public.leads;
-- DROP FUNCTION IF EXISTS public.leads_set_updated_at();
-- DROP TABLE    IF EXISTS public.leads;
```

⚠️ هشدارِ خودِ فایل: **اگر جدول دادهٔ واقعی دارد `DROP TABLE` نزن** — لیدِ واقعی
از بین می‌رود. روی staging پس از تمرین بی‌خطر است.

## گام ۵ — ثبت

`MIGRATION-LEDGER.md` فقط پس از اجرای واقعی به‌روز می‌شود، با تفکیکِ صریحِ
**staging از Production**. اجرای staging **به‌هیچ‌وجه** ردیفِ Production را
`APPLIED` نمی‌کند.

## وضعیتِ فعلی

**اجرا شد — `PARTIALLY_PROVEN` (۲۰۲۶-۰۷-۳۰).** هیچ لیدِ واقعی ساخته یا فرستاده نشد؛
همهٔ داده‌ها مصنوعی و برچسب‌خورده بودند.

### چه اثبات شد ✅

| بند | شاهد |
|---|---|
| migration روی staging | جدول ساخته شد · `relrowsecurity=true` · ۲ سیاست · ۵ ایندکس (PK + ۴) · ۴ قید · تریگرِ `updated_at` شلیک می‌کند |
| `anon` قفل است | `has_table_privilege('anon','public.leads','SELECT') = false` (و `INSERT` هم) |
| ردیفِ MySQLِ مینی‌اپ | لیدِ مصنوعی در MySQLِ ایزوله ثبت شد و **منبعِ حقیقت** ماند |
| دقیقاً یک تلاشِ خروجی | یک خطِ `lead_webhook_failed` و یک `POST /api/leads/webhook` — نه بیشتر |
| احرازِ وبهوک (**رفعِ `B-020`**) | با سکرتِ درست پاسخ **۴۰۱ نبود**؛ به `db_insert_failed` رسید، یعنی سکرت مطابقت کرد و payload از اعتبارسنجی گذشت |
| شکست دیده می‌شود (**رفعِ `B-019`**) | پاسخِ non-2xx به‌عنوانِ شکست لاگ شد، نه موفقیت |
| هیچ دادهٔ شخصی در لاگ | جست‌وجوی متنی در لاگِ هر دو سرویس: نام، تلفن، پیام و سکرت **صفر بار** |
| تمرینِ شکست | سکرتِ عمداً غلط → **۴۰۱**، لیدِ MySQL سالم ماند، بازگرداندنِ تنظیمات مسیر را برگرداند |
| سه حالتِ قابلِ تفکیک | ۴۰۱ (سکرتِ غلط) · ۵۰۰ (احراز درست، DB نارس) · موفقیت — از هم قابلِ تشخیص‌اند |

### چه اثبات **نشد** ❌

**هاپِ آخر: نوشتنِ واقعیِ ردیف در `public.leads` از مسیرِ اپلیکیشن.**
دو مانعِ محیطی — نه نقصِ کد:

- `B-029` — کلیدِ service-roleِ staging از هیچ ابزارِ در دسترسی قابلِ دریافت نیست.
- `B-030` — سیاستِ شبکهٔ محیطِ اجرا `*.supabase.co` را مسدود می‌کند
  (`Host not in allowlist: …` در لاگِ خودِ اپلیکیشن).
- `B-031` — MCPِ Vercel ابزارِ متغیرِ محیطی ندارد.

### دقیقاً چه چیزی این را باز می‌کند

زنجیره در **دو نقطهٔ مستقل** قطع است؛ رفعِ یکی کافی نیست:

| نقطه | چه لازم است |
|---|---|
| **گرفتنِ کلید** | یک Supabase Personal Access Token به‌عنوانِ `SUPABASE_ACCESS_TOKEN` در محیطِ سشن + بازبودنِ `api.supabase.com` |
| **نوشتن در Supabase** | بازبودنِ egress به `*.supabase.co` (یا اجرای تمرین از محیطی که خروجی‌اش باز است، مثلِ خودِ Vercel Preview) |
| **پیکربندیِ Preview** | ست‌کردنِ متغیرها روی اسکوپِ **Preview** در پنلِ Vercel (یک‌بار، دستی) — چون ابزارِ env در MCP نیست |

با این سه، بقیهٔ تمرین بدونِ دخالتِ آرش تا انتها اجرا می‌شود؛ همهٔ مراحلِ دیگر
از قبل نوشته و آزموده شده‌اند.

بنابراین **«ردیف در Supabase ساخته شد» و «ادمین آن را می‌بیند» هنوز `UNPROVEN` است**
و `B-001`/`B-002`/`B-003` باز می‌مانند.

> یک بررسیِ جداگانه انجام شد و **عمداً به‌عنوانِ اثباتِ سرتاسری حساب نمی‌شود**:
> رکوردی که `parseLeadPayload()` تولید می‌کند مستقیماً در `public.leads` درج شد تا
> فقط **قراردادِ اسکیما** سنجیده شود (همهٔ فیلدها حفظ شدند، UTF-8 سالم، پیش‌فرض‌ها و
> تریگر درست). این درجِ مستقیم است، نه مسیرِ مینی‌اپ. رکورد بعد از سنجش حذف شد.

### یافتهٔ امنیتیِ این تمرین

`REVOKE ALL … FROM anon` کافی نبود. اندازه‌گیریِ واقعی نشان داد `authenticated`
امتیازِ `DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE` داشت. چون
**RLS روی `TRUNCATE` اعمال نمی‌شود**، هر کاربرِ لاگین‌کردهٔ عادی می‌توانست کلِ جدولِ
لید را خالی کند. Security Advisor آن را نگرفت. فایل اصلاح شد و
`lib/leads/grants.test.ts` جلوی برگشتش را می‌گیرد.
