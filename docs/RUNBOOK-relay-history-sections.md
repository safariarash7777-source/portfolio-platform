# Runbook — فعال‌کردنِ مهارِ رشدِ `ir_market_history`

> **وضعیت: اجرا نشده.** این سند فقط دستورالعمل است.
> پیش‌نیاز: merge شدنِ PR #119.

## چرا این Runbook لازم است

تغییرِ `IR_HISTORY_SECTIONS` در `relay/server.mjs` است، و رله **روی Vercel اجرا
نمی‌شود**. روی Liara داخلِ ایران اجرا می‌شود، چون منابعِ ایرانی به IPِ خارجی
۴۰۳ می‌دهند.

> ⚠️ **merge کردنِ PR و دیپلویِ Vercel به‌تنهایی رشد را متوقف نمی‌کند.**
> تا وقتی رله روی Liara دوباره مستقر نشود، همچنان هر ۳۰ دقیقه چهار بخش
> نوشته می‌شود و جدول روزی ۷.۷ MB بزرگ‌تر می‌شود.

این تنها گامی از برنامهٔ مهار است که **قبل از** هر تصمیمِ حذف اثر می‌گذارد، و
تنها گامی است که هیچ داده‌ای را لمس نمی‌کند.

## دسترسی

نویسندهٔ این سند به Liara **دسترسی ندارد**. هیچ استقراری انجام نشده و
انجام‌شده اعلام نمی‌شود. گام‌های زیر برای اپراتور است.

## گام‌ها

### ۱) متغیر را ست کنید (اختیاری — پیش‌فرضِ کد از قبل درست است)
پس از merge، پیش‌فرضِ `IR_HISTORY_SECTIONS` برابرِ `gold,currency` است، پس
**نیازی به ست‌کردن نیست**. فقط اگر می‌خواهید رفتارِ قبلی موقتاً برگردد:

```
IR_HISTORY_SECTIONS=gold,currency,funds,stocks
```

### ۲) رله را روی Liara دوباره مستقر کنید
طبقِ رویهٔ معمولِ سرویسِ رله (`relay/README.md`). این تنها اقدامی است که
تغییر را فعال می‌کند.

### ۳) اثباتِ اینکه فقط دو بخش نوشته می‌شود
endpointِ وضعیتِ رله را بخوانید. باید ببینید:

```json
"historySections": { "written": ["gold", "currency"], "missing": [] }
```

اگر `written` هنوز چهار عضو دارد، استقرار انجام نشده یا env قدیمی مانده.
اگر `missing` خالی نیست، **منبع** آن بخش را برنگردانده — این یک نقصِ فید است
و باید جدا بررسی شود، نه نادیده گرفته شود.

### ۴) دو چرخهٔ واقعی را ببینید
رله هر ۳۰ دقیقه یک نمونه می‌نویسد (`HISTORY_INTERVAL_MS`). **دستِ‌کم ۶۵
دقیقه** صبر کنید تا دو چرخهٔ کامل بگذرد، سپس تأیید کنید که هیچ ردیفِ تازه‌ای
از دو بخشِ بی‌خواننده ساخته نشده:

```sql
-- فقط SELECT. باید صفر برگرداند.
select count(*) as new_unread_rows
from public.ir_market_history
where section in ('stocks','funds')
  and captured_at > '<زمانِ استقرار به UTC>';
```

و برای اطمینان از اینکه فید **نمرده** (کوچک‌ماندن به‌خاطر قطعی نباشد):

```sql
select section, count(*) as rows_since_deploy, max(captured_at) as newest
from public.ir_market_history
where captured_at > '<زمانِ استقرار به UTC>'
group by section;
```

انتظار: دو ردیف (`gold`, `currency`)، هرکدام ≥۲ نمونه.
اگر صفر ردیف برگشت، مشکل استقرار نیست — **رله داده نمی‌فرستد**.

### ۵) نمای سلامت را ببینید
`/admin/health` دو سیگنالِ «نگهداشت» دارد. پس از استقرار باید `ok` بمانند و
`retention.budgetChecked` همچنان `false` باشد (حجمِ بایتی از سایت خواندنی
نیست — این نقص نیست، محدودیتِ اعلام‌شده است).

## معیارِ پذیرش

| بررسی | انتظار |
|---|---|
| `historySections.written` | دقیقاً `["gold","currency"]` |
| `historySections.missing` | `[]` |
| ردیفِ تازهٔ `stocks`/`funds` پس از استقرار | **۰** |
| نمونهٔ تازهٔ `gold` و `currency` در ۶۵ دقیقه | **≥۲ هرکدام** |
| سیگنال‌های نگهداشت در `/admin/health` | `ok`، نه `unknown` |

هر پنج مورد باید هم‌زمان برقرار باشد. چهار موردِ اول بدونِ موردِ چهارم
می‌تواند یعنی «فید مرده»، نه «مهار موفق».

## پس از این Runbook

رشد متوقف می‌شود ولی **۳۲۷ MB موجود سرِ جایش می‌ماند**. آزادکردنش گامِ ۲
برنامهٔ `DATA-RETENTION-AND-ARCHIVE-PLAN.md` است و پیش‌نیازش export و
read-back است — حتی برای دادهٔ بی‌خواننده.
