# معماری Hot/Cold — Supabase و Cloudflare R2

> وضعیت: **پیشنهاد، منتظر تأیید Command Center.** هیچ بخشی اجرا نشده.
> مبنای عددی: `.planning/2026-08-28-data-quota-recovery/findings.md`
> (اندازه‌گیریِ زندهٔ Production، ۲۸ اوت ۲۰۲۶).

## چرا این سند لازم شد

دیتابیس ۱۱۳۰ MB است و سقفِ رایگان ۵۰۰ MB. ولی مسئله آن چیزی نیست که در نگاه
اول به‌نظر می‌رسد:

| | حجم | بازهٔ زمانی | رشد | خوانده می‌شود؟ |
|---|---|---|---|---|
| `symbol_history` | ۷۴۲ MB | **۲۵ سال** | ۵۷–۷۲ MB/سال | بله، ۸ مصرف‌کننده |
| `ir_market_history` | ۳۴۸ MB | **۴۵ روز** | **۲.۸ GB/سال** | فقط ۶٪‌اش |

جدولِ بزرگ‌تر یک **دارایی** است؛ جدولِ کوچک‌تر یک **نشتی**. هر طراحی‌ای که
این دو را یکسان ببیند، تاریخچه را قربانیِ نشتی می‌کند.

## اصل حاکم

> داده جایی می‌ماند که **سؤالی** به آن تکیه دارد. اگر هیچ سؤالی به آن تکیه
> نکند، اصلاً جمع نمی‌شود (قاعدهٔ **Q3** اسکیلِ `iran-market-data`). اگر سؤال
> نادر و تحملِ تأخیر داشته باشد، سرد می‌شود. اگر روزانه باشد، گرم می‌ماند.

## لایهٔ گرم — Supabase

| دسته | جدول‌ها | چرا گرم |
|---|---|---|
| وضعیتِ امروز | `ir_market_snapshots`, `market_breadth`, `index_history`, `fx_rates` | هر بار بازکردنِ سایت |
| روندِ عمومی | `ir_market_history` — **فقط `gold` و `currency`** | `/market` → `TrendChart` |
| تاریخچهٔ عملیاتی | `symbol_history` تا افقِ محاسباتی | رصد، بازده، رژیم، نمودارِ نماد، بک‌تست |
| کاربر و کسب‌وکار | `profiles`, `payments`, `entitlements`, `webinars`, `waitlist`, CRM | تراکنشی |
| تحلیل و تصمیم | `signals`, `weekly_outlooks`, `codal_reports`, `content_hub`, `audit_log` | کارنامهٔ append-only |

**افقِ محاسباتیِ گرم** از خودِ کد درآمده، نه از حدس. عمیق‌ترین مصرف‌کننده‌ها:

| مصرف‌کننده | عمق |
|---|---|
| `radarData.ts` | ۱۰ روز |
| `avgVolume.ts` | ۴۵ روز |
| `bulkReturns.ts` | ۱۰۵ روز |
| `history.ts` (نمودارِ نماد) | ۴۰۰ روزِ معاملاتی |
| `terminal/allocation` (بک‌تست) | **۱٬۵۰۰ روز (~۶ سال)** — ولی فقط برای **۶ نماد** |
| `api/data/[symbol]/history.csv` | **کلِ ۲۵ سال، هر نماد** |

پس افقِ گرمِ پیشنهادی: **۶ سال برای همه**. این ردیفِ آخر است که تعیین می‌کند
دادهٔ قدیمی‌تر **آرشیو** شود نه **حذف**.

## لایهٔ سرد — Cloudflare R2

فقط دو چیز سرد می‌شوند:

1. `symbol_history` قدیمی‌تر از افقِ گرم — امروز ۱٬۰۵۰٬۰۵۵ ردیف (۵۰.۱٪)، ۲۲۴ MB heap.
2. `ir_market_history` بخش‌های `gold`/`currency` خارج از پنجرهٔ نگهداشت.
3. `ir_market_history` بخش‌های `stocks`/`funds` — **یک‌بار، پیش از حذف.**

⚠️ نسخهٔ اولِ همین سند نوشته بود این دو بخش آرشیو نمی‌شوند چون «خوانده
نشده‌اند و آرشیوکردنِ زباله هزینه را جابه‌جا می‌کند». آن استدلال غلط بود:
**بکاپِ restore-verified نداریم**، پس «فعلاً خواننده ندارد» با «بازگرداندنی
نیست» یکی گرفته شده بود. ۳۲۷ MB دادهٔ واقعیِ تابلو است؛ هزینهٔ نگهداریِ
یک‌بارهٔ فشرده‌اش روی R2 ناچیز است و در برابرِ حذفِ برگشت‌ناپذیر قابلِ قیاس
نیست. هفت گیتِ اجباری در `DATA-RETENTION-AND-ARCHIVE-PLAN.md` §گام ۲.

### چیدمان

```
r2://arash-market-archive/
  symbol_history/v1/year=2001/part-0000.parquet
  symbol_history/v1/year=2002/...
  ir_market_history/v1/section=gold/year=2026/month=07/part-0000.parquet
  _manifests/symbol_history/v1/year=2001.json
```

پارتیشن بر اساس **سال** (نه نماد): پرس‌وجوی غالبِ لایهٔ سرد «کلِ تاریخچهٔ یک
نماد» است و ۲۵ فایلِ سالانه کمتر از ۱٬۱۲۶ فایلِ نمادی هزینه دارد؛ Parquet هم
با ستونیِ فشرده، فیلترِ نماد را ارزان می‌کند.

فرمت **Parquet + zstd**. تخمینِ ۲۲۴ MB heap ⇒ حدود ۲۵–۴۰ MB روی R2
(`UNVERIFIED` تا اولین export واقعی؛ نسبت باید اندازه‌گیری شود نه ادعا).

### Manifest — شرطِ «آرشیوشده» بودن

هر فایل یک manifest کنارش دارد:

```json
{
  "schema_version": "symbol_history.v1",
  "source_table": "public.symbol_history",
  "partition": { "year": 2001 },
  "row_count": 41822,
  "time_range": { "min_trade_date": "2001-03-25", "max_trade_date": "2001-12-19" },
  "sha256": "…",
  "exported_at": "2026-…Z",
  "exporter": "scripts/archive/export-symbol-history.mjs@<commit>",
  "columns": ["id","symbol","trade_date","captured_at","open","high","low","close", "..."]
}
```

**هیچ ردیفی «آرشیوشده» شمرده نمی‌شود مگر هر پنج شرط برقرار باشد:**

1. `row_count` فایل با `COUNT(*)` همان بازه در Postgres **برابر** باشد.
2. `sha256` محاسبه و در manifest ثبت شده باشد.
3. فایل **دوباره از R2 خوانده** و checksumش تطبیق داده شود.
4. چند پرس‌وجوی نمونه و **یک بک‌تستِ واقعی** روی آرشیو اجرا و خروجی‌اش با
   همان بک‌تست روی Postgres مقایسه شود.
5. مسیرِ **Restore** اثبات شود: بازگرداندنِ یک پارتیشن به جدولِ موقت و تطبیقِ
   ردیف‌به‌ردیف.

تا وقتی این پنج شرط برای یک پارتیشن سبز نشده، **هیچ ردیفی از Production حذف
نمی‌شود**. ترتیب همیشه: export → verify → restore-drill → (تأیید مالک) → حذف.

### خواندنِ آرشیو از محصول

`api/data/[symbol]/history.csv` تنها مسیری است که به دادهٔ سرد نیاز دارد.
پیشنهاد: همان مسیر اول Postgres را می‌خواند و اگر بازهٔ درخواستی از افقِ گرم
عقب‌تر برود، پارتیشن‌های R2 را هم می‌خواند و به هم می‌چسباند. اگر R2 در دسترس
نبود، **صریح** بگوید تاریخچه ناقص است — هرگز یک سریِ کوتاه‌شده را به‌جای
کامل جا نزند.

## آنچه این معماری حل نمی‌کند

R2 حجمِ Supabase را **خودکار** کم نمی‌کند. آرشیو فقط حذف را **بی‌خطر** می‌کند؛
آزادسازیِ فضا کارِ جداگانه‌ای است با قفل و ریسکِ خودش — در
`docs/DATA-RETENTION-AND-ARCHIVE-PLAN.md`.
