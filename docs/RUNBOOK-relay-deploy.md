# استقرار رله — و چرا مسیر خودکارش کار نمی‌کند

> **وضعیت `B-053`:** یکپارچه‌سازیِ GitHub→Liara برای اپِ `arsadata` **هرگز یک
> استقرارِ موفق نداشته**. ۱۵۶ رکوردِ استقرار از ۲۰۲۶-۰۷-۱۶ تا امروز؛ ۱۶ نمونهٔ
> پخش‌شده در کلِ بازه — از **اولین** رکورد تا آخرین — همگی `failure`.
>
> یعنی این یک **رگرسیون نیست** که بشود با bisect پیدایش کرد. پیکربندی از روزِ
> اول کار نکرده. پس هر نسخه‌ای از رله که تا امروز روی Production رفته، از
> **مسیرِ دیگری** رفته (به احتمال زیاد `liara` CLI از دستگاهِ آرش) و
> **شناسهٔ نسخه‌اش هیچ‌جا ثبت نشده**.

## آنچه از سمتِ مخزن **اثبات** شده

| بررسی | نتیجه |
|---|---|
| آیا artifact قابلِ اجراست؟ | ✅ `node relay/server.mjs` روی `main@1d7e8f1` بالا می‌آید، `/healthz` → `ok` |
| وابستگیِ خارجی؟ | ❌ **هیچ.** `relay/package.json` نه `dependencies` دارد نه `devDependencies`؛ همهٔ importها `node:*` هستند. پس نه `npm ci` لازم است نه lockfile |
| دستورِ اجرا | `node server.mjs` (از `relay/package.json`) |
| پورت و پلتفرم | `relay/liara.json`: `platform: node`، `port: 3400` |
| نسخهٔ Node | `relay/package.json` → `>=18`؛ ⚠️ **ریشهٔ مخزن** `>=20` می‌خواهد و اپِ Next است (`next start`) |

⚠️ **آنچه اثبات **نشده**:** تنظیماتِ واقعیِ کنسول — مخزن، branch، پوشهٔ build،
platform، دستورِ start، پورت و نسخهٔ Node. فایل‌های بالا **نیت** مخزن‌اند، نه
پیکربندیِ پلتفرم. تا وقتی لاگِ بیلد خوانده نشود، **هیچ علتی قطعی نیست** —
از جمله این فرضیه که بیلد از ریشهٔ مخزن اجرا می‌شود.

## پیش‌پروازِ اجباری — پیش از هر استقرار

هدف: استقرارِ این نسخه نباید ناخواسته enforcementِ وابسته به `phase28` را
روشن کند. **اندازه‌گیری‌شده روی همان artifact، نه استنتاج از کد:**

```
$ RELAY_TOKEN=… PORT=3499 node relay/server.mjs
$ curl -H "Authorization: Bearer …" localhost:3499/debug
historySections  : {"written": ["gold","currency"], "missing": []}
brsapiLegacy.enforced : false
brsapiClient.enabled  : false
```

هر سه باید همین باشند. اگر `enforced` برابر `true` بود، یعنی
`BRSAPI_BUDGET_ENFORCE_LEGACY` در محیطِ مقصد ست شده — **پیش از استقرار
برش دار**؛ هر دو پرچم صریحاً `=== "1"` می‌خواهند و پیش‌فرضشان خاموش است.

## مسیرِ استقرار — نحوِ **راستی‌آزمایی‌شده**، نه حدس

ابزار: **`@liara/cli@9.5.1`** (`liara/9.5.1 linux-x64 node-v22.22.2`). همهٔ
پرچم‌های زیر از `liara <cmd> --help` همان نسخه خوانده شده‌اند.

> نسخهٔ قبلیِ این سند نحوِ CLI را «تأییدنشده» گذاشته بود. حالا تأیید شده.
> ⚠️ روی لپ‌تاپ اول `liara --version` را ببین؛ اگر نسخه فرق داشت، پرچم‌ها را
> با `--help` همان نسخه تطبیق بده.

### گامِ ۰ — ورود (فقط تعاملی، روی همان لپ‌تاپ)

```
npx --yes @liara/cli@9.5.1 login
```

هیچ توکنی در چت رد و بدل نمی‌شود.

### گامِ ۱ — وضعیتِ **واقعیِ** اپِ در حالِ اجرا را بخوان

اینجا همان چیزی خوانده می‌شود که مأموریت خواسته: «خاموش‌بودنِ پرچم‌ها در تستِ
محلی کافی نیست.» این دستور **مقدارِ واقعیِ داخلِ کانتینرِ در حالِ اجرا** را
می‌دهد — و عمداً فقط همین چند کلید را چاپ می‌کند، **نه هیچ سکرتی**:

```
npx @liara/cli@9.5.1 shell -a arsadata -c 'node -e "const e=process.env;console.log(JSON.stringify({node:process.version,PORT:e.PORT??null,IR_HISTORY_SECTIONS:e.IR_HISTORY_SECTIONS??null,BRSAPI_CLIENT_ENABLED:e.BRSAPI_CLIENT_ENABLED??null,BRSAPI_BUDGET_ENFORCE_LEGACY:e.BRSAPI_BUDGET_ENFORCE_LEGACY??null,BRSAPI_KEY_SET:Boolean(e.BRSAPI_KEY),SUPABASE_URL_SET:Boolean(e.SUPABASE_URL)}))"'
```

**شرطِ عبور:**

| کلید | مقدارِ لازم | اگر نبود |
|---|---|---|
| `BRSAPI_CLIENT_ENABLED` | `null` یا هر چیزی جز `"1"` | ⛔ **استقرار نکن.** اول در کنسول برش دار |
| `BRSAPI_BUDGET_ENFORCE_LEGACY` | `null` یا هر چیزی جز `"1"` | ⛔ **استقرار نکن** — با `phase28` اجرانشده، این یعنی رله در نبودِ شمارنده **می‌ایستد** |
| `IR_HISTORY_SECTIONS` | `null` (تا پیش‌فرضِ `gold,currency` اثر کند) | اگر ست است و چهار بخش دارد، همان را در کنسول بردار |
| `SUPABASE_URL_SET` | `true` | بدونِ آن رله اصلاً نمی‌نویسد |

`BRSAPI_KEY_SET` و `SUPABASE_URL_SET` عمداً **بولین**اند — مقدار چاپ نمی‌شود.

### گامِ ۲ — لاگِ فعلی و نقطهٔ بازگشت را ثبت کن

```
npx @liara/cli@9.5.1 logs -a arsadata -t -s "2 hours ago" | tail -40
```

شناسهٔ release در این CLI به شکلِ `v1`, `v2`, … است (`logs -r <release>`).
**شمارهٔ releaseِ فعلی را همین‌جا یادداشت کن** — نقطهٔ بازگشت است.

⚠️ **در `@liara/cli@9.5.1` دستورِ `rollback` وجود ندارد.** فهرستِ کاملِ
دستورها: `create, delete, deploy, help, init, login, logs, restart, shell,
start, stop, update-port, version`. پس بازگشت یعنی **استقرارِ دوبارهٔ SHAِ
قبلی** با همان دستورِ گامِ ۳؛ و فهرستِ release‌ها فقط در کنسول دیده می‌شود.

### گامِ ۳ — استقرار

```
cd <مسیر مخزن>
git fetch origin && git checkout 1d7e8f11084dec6fd43c81fe46a49baed6fe15bf
npx @liara/cli@9.5.1 deploy -a arsadata --path relay -m "relay @ 1d7e8f1"
```

چرا این شکل:

- `--path relay` → پوشهٔ مبدأ **`relay/` است، نه ریشهٔ مخزن**. این همان نقطه‌ای
  است که در استقرارِ خودکار مشکوک است.
- `--liara-json` پیش‌فرضش `PATH/liara.json` است، پس **`relay/liara.json`
  خودکار خوانده می‌شود** (`platform: node`, `port: 3400`). لازم نیست
  `--platform` یا `-p` بدهی.
- `-m "relay @ 1d7e8f1"` → پیامِ release. **تنها جایی است که SHA به نسخهٔ
  مستقر گره می‌خورد** — تا امروز هیچ نسخهٔ رله شناسه‌ای نداشته.
- `liara stop` یا `delete` **نزن**. `deploy` خودش جایگزین می‌کند؛ نسخهٔ فعلی
  تا بالا آمدنِ نسخهٔ نو سرِ جایش می‌ماند.

بستهٔ آپلود: `relay/` = **۷۸۴ کیلوبایت**، ۳۳ فایل، شاملِ تست‌ها. اسکنِ سکرت
روی همین درخت سبز است و `.liaraignore` وجود ندارد.

### آنچه این CLI **نمی‌تواند** بخواند

`9.5.1` هیچ دستوری برای خواندنِ تنظیماتِ اپ ندارد: platform، نسخهٔ Node،
دستورِ start، تعدادِ replica، فهرستِ متغیرها، و فهرستِ release‌ها. پس آن شش
تنظیمِ خواسته‌شده در مأموریت **فقط از کنسول** خواندنی‌اند. گامِ ۱ بالا تنها
راهِ CLIای است که به بخشی از همان اطلاعات (نسخهٔ Node و مقدارِ دو پرچم)
می‌رسد.

## پذیرش — دو چرخهٔ نوشتن

چرخهٔ تاریخچه هر **۳۰ دقیقه** است، پس دو چرخه ≈ **۶۰ دقیقه** پس از استقرار.

```sql
select section,
       count(*) filter (where captured_at >= now() - interval '70 minutes') as rows_70m,
       max(captured_at) as newest
from ir_market_history group by section order by section;
```

| بخش | انتظار |
|---|---|
| `stocks`, `funds` | `rows_70m = 0` · `newest` **ثابت** روی زمانِ پیش از استقرار |
| `gold`, `currency` | `rows_70m ≥ 2` · `newest` تازه |

و زنده‌بودنِ بقیهٔ مسیرها:

```sql
select updated_at from ir_market_snapshots where key='latest';
```

باید تازه باشد — یعنی تابلوی زنده، صفحهٔ صندوق و `symbol-detail` قطع نشده‌اند.

⚠️ **دادهٔ قبلی حذف نمی‌شود.** این تغییر فقط **نوشتن** را می‌ایستاند؛ حجمِ
امروزِ جدول کم نمی‌شود.

⚠️ دو چرخه **پایداریِ بلندمدت را اثبات نمی‌کند** — فقط می‌گوید تغییر در همان
یک ساعت اثر کرده.

## چرا این کار از جلسهٔ عامل انجام نمی‌شود

این جلسه روی لپ‌تاپ اجرا نمی‌شود. شاهد: `hostname=vm`، `whoami=root`،
`/proc/1/sched → process_api` — یعنی کانتینرِ اجرای ابری. `liara` نصب نیست و
`~/.liara` (اعتبارنامهٔ ورود) وجود ندارد. ورود به Liara تعاملی است و
**نباید** توکنش از چت عبور کند.

پس گام‌های ۰ تا ۳ بالا باید روی **همان لپ‌تاپی** اجرا شوند که به Liara لاگین
است. خروجیِ گامِ ۱ و شمارهٔ releaseِ گامِ ۲ را بفرست تا پذیرش دنبال شود.
