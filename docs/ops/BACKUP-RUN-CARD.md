# کارتِ اجرای بکاپ و بازیابی — یک صفحه، آمادهٔ اجرا

> **این سند دستور نمی‌دهد که «الان اجرا کن».** آماده است تا هر وقت آرش خواست،
> بدونِ فکرکردن به جزئیات، اجرا شود.
>
> رویهٔ کاملِ ویندوز: [`../RUNBOOK-backup-windows.md`](../RUNBOOK-backup-windows.md)

---

## ۰. چرا این دروازه هست

سازمانِ Production روی پلنِ **رایگان** است و Supabase برایش بکاپِ خودکار
نمی‌گیرد. تا نقطهٔ بازگشتِ **اثبات‌شده** نداشته باشیم، هیچ migrationی روی
Production اجرا نمی‌شود. این قاعده دور زده نمی‌شود.

**رمز باید دستِ اپراتور بماند و هرگز وارد چت نشود.** پس اجرای واقعی ذاتاً دستِ
آرش است: اسکریپت رمز را در ورودیِ مخفیِ همان پنجره می‌پرسد.

---

## ۱. پیش‌نیاز (یک‌بار)

| ابزار | چرا |
|---|---|
| **Docker Desktop** (باز و بالا آمده، با `docker compose`) | هم dump می‌گیرد، هم بازیابی را در استکِ ایزوله می‌آزماید |
| **Node.js LTS** | `npx` برای Supabase CLI و `compare.mjs` |
| **git** | برای گرفتنِ **دقیقاً همان نسخهٔ آزموده** |

**لازم نیست:** تغییرِ تنظیمِ عمومیِ Docker Desktop (`"ip"`) یا به‌روزکردنِ Supabase CLI.
مقصدِ بازگردانی دیگر `supabase start` نیست؛ یک استکِ اختصاصی از
`scripts/backup/verify-stack.compose.yml` است:

- **هیچ پورتی منتشر نمی‌کند** و روی شبکهٔ Dockerِ `internal` است — نه از شبکهٔ
  محلی دیده می‌شود، نه به اینترنت راه دارد (پس jobهای pg_cron یا درخواست‌های
  pg_netِ بازگردانی‌شده به سرویسِ واقعی نمی‌رسند). اسکریپت این را روی
  **کانتینرهای در حالِ اجرا** می‌سنجد (`docker ps`، `HostConfig.PortBindings`،
  `PublishAllPorts`، شبکه‌ها و `Internal`) و در غیرِ این صورت پیش از ورودِ داده
  متوقف می‌شود.
- تصویرها با **digest** pin شده‌اند: Postgres `17.6.1.167`، Auth `v2.197.0`، Storage
  `v1.77.6`. پیش از بازگردانی، **ساختارِ** `auth` و `storage`ِ مقصد با Production
  دوطرفه مقایسه می‌شود (`managed-schemas.sql`)، نه فقط شمارهٔ نسخه.
- Supabase CLI فقط برای dump است و روی `supabase@2.117.0` pin شده؛ پیش از
  پرسیدنِ رمز یک بار اجرا می‌شود.

⚠️ اگر ریپو پیش از این نسخه روی ویندوز checkout شده، `scripts/backup/pgurl.sh`
ممکن است CRLF باشد (`core.autocrlf=true`) و داخلِ کانتینر بشکند. اسکریپت این را
پیش از هر کار می‌گیرد و دستورِ اصلاح را چاپ می‌کند.

## ۲. دستور

روی **ویندوز**، در **Windows PowerShell**، **داخلِ پوشهٔ ریپو**:

```powershell
git fetch origin claude/backup-verify-compose
git checkout --detach origin/claude/backup-verify-compose
git rev-parse --short HEAD        # باید با SHAِ اعلام‌شده در PR یکی باشد
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\backup-production.ps1
```

بکاپ در `%USERPROFILE%\supabase-backups\prod-<زمان>` ساخته می‌شود — **بیرون از ریپو**؛
اگر مقصد داخلِ یک مخزنِ گیت باشد، اسکریپت اجرا نمی‌شود.

روی **مک یا لینوکس**: `bash scripts/backup-production.sh`

اسکریپت رشتهٔ اتصال را **می‌پرسد** (ورودیِ مخفی) و آن را روی دیسک نمی‌نویسد، در
تاریخچهٔ شل نمی‌گذارد و چاپ نمی‌کند. رشته را از **Supabase Dashboard → پروژه →
Connect → Session pooler** بردار.

> ⚠️ **رشتهٔ اتصال را در چت نگذار.**

## ۳. معیارِ موفقیت — «فایل هست» کافی نیست

| # | معیار | چطور سنجیده می‌شود |
|---|---|---|
| ۱ | مقصد ایزوله است | هیچ پورتِ منتشرشده، هیچ binding، شبکهٔ `internal` — روی کانتینرهای در حالِ اجرا |
| ۲ | مقصد وفادار است | ساختارِ `auth`/`storage` با Production **عیناً** یکی (`managed-schemas.sql`، دوطرفه) |
| ۳ | بازگردانی در **یک تراکنش** | `ON_ERROR_STOP=1` + **کدِ خروجیِ `psql`**؛ خطا ⇒ کلِ تراکنش برمی‌گردد |
| ۴ | امتیازها دقیقاً همان Production | `restore-prelude.sql` امتیازِ پیش‌فرضِ نقشِ اجراکننده را پیش از `schema.sql` برمی‌دارد؛ بدونِ آن `anon` روی جدولِ revokeشده دوباره دسترسی می‌گرفت |
| ۵ | **شمارشِ دقیقِ** ردیف‌ها و اثرِ انگشتِ ساختاری، دوطرفه | `inventory.sql` + `compare.mjs` (با `search_path`ِ ثابت) |
| ۶ | هشِ رمزِ کاربران دست‌نخورده | خطِ `digest|auth.users.credentials` در همان مقایسه |

`compare.mjs` فقط با **صفر اختلاف در هر دو جهت** کدِ ۰ می‌دهد.

**خروجیِ سبز:** `result: PASS (structure verified - row counts exactly equal)` و کدِ خروجیِ `0`.

- کدِ `2` = PARTIAL (جدولی حینِ dump نوشته شده) — **PASS نیست**.
- اگر dump گرفته شد ولی بازگردانی یا مقایسه نه، فایل‌ها **نگه داشته می‌شوند** و
  MANIFEST می‌نویسد `RESTORE UNVERIFIED` — آن‌ها را پاک نکن.

⚠️ **آنچه در بکاپ نیست:** jobهای pg_cron. `supabase db dump` جدولِ `cron.job` را
نمی‌گیرد (اندازه‌گیری‌شده). اسکریپت تعدادشان را در MANIFEST می‌نویسد
(`NOT IN BACKUP: pg_cron jobs - production has N`). پس از هر بازگردانیِ واقعی باید
دستی ساخته شوند.

## ۴. بعد از سبزشدن

۱. فقط `MANIFEST.txt` را گزارش کن (**نه محتوا، نه رشتهٔ اتصال**).
۲. آن‌وقت — و فقط آن‌وقت — ترتیبِ migrationهای `docs/MARKET-CORE-AUDIT.md` §۴.۴
   قابلِ اجراست، با تصمیمِ جداگانهٔ آرش برای هر کدام.

⚠️ پوشهٔ بکاپ دادهٔ واقعیِ اعضا دارد. هرگز commit نکن، در GitHub/تلگرام/ایمیل نگذار.

## آزمونِ پذیرش — آنچه واقعاً اجرا شد (۲۰۲۶-۰۹-۲۳، لپ‌تاپِ آرش)

خودِ `scripts/backup-production.ps1` در **Windows PowerShell 5.1.19041.6456**، Docker
Desktop 29.6.2، با **دادهٔ مصنوعی** (یک استکِ Supabaseِ مبدأ با همین compose، بدونِ
پورتِ منتشرشده؛ دو کاربر از APIِ Auth، ۵۰۰ ردیفِ فارسی، RLS، policy، نقشِ سفارشی،
job‌ِ cron). رمز از راهِ خودِ `Read-Host -AsSecureString` وارد شد (نوشتن در بافرِ
ورودیِ همان کنسول)، نه pipe.

| مورد | نتیجه |
|---|---|
| مسیرِ کامل | PASS، کد ۰، ۱۵۶ موردِ فهرست، ساختارِ auth/storage یکسان |
| ایزوله‌بودن | ۳ کانتینر، `bindings={}`، `publishAll=false`، شبکهٔ `internal=true`؛ هیچ listenerِ تازه روی ویندوز؛ خروج به اینترنت بسته؛ از شبکهٔ bridge دسترس‌ناپذیر |
| هشِ رمز | md5ِ هشِ هر کاربر و خطِ digest در مبدأ و مقصد یکسان |
| شمارشِ کاربران | `auth.users` ۲ = ۲ |
| ورود | ورودِ هر دو کاربرِ مصنوعی روی Authِ **بازگردانی‌شده**: HTTP 200 + توکن؛ رمزِ غلط: 400 |
| رمزِ غلط / ورودیِ خراب / ورودیِ خالی | کد ۱، پیش از هر dump |
| خطای میانهٔ بازگردانی (پس از بارشدنِ `auth.users`) | کد ۳؛ مقصد پس از شکست: ۰ جدول، ۰ کاربر، ۰ نقشِ سفارشی — rollbackِ کامل؛ فایل‌ها ماندند، `RESTORE UNVERIFIED` |
| بکاپِ ناقص (۴۰۰ از ۵۰۰ ردیف حذف) | بازگردانی ۰ ولی مقایسه FAIL، کد ۱ |
| `data.sql` خالی | کد ۱، `RESTORE UNVERIFIED`، فایل‌ها ماندند |
| نشتِ رمز | در هیچ‌کدام از ۷۴ فایلِ خروجی و در `docker inspect`ِ مقصد نیست |
| پاکسازی | در موفقیت و شکست فقط منابعِ همان اجرا (با برچسب) حذف شد؛ چیزی نماند |

**این PASSِ مصنوعی است، نه PASSِ Production.** بکاپِ واقعی فقط با اجرای آرش معلوم می‌شود.
