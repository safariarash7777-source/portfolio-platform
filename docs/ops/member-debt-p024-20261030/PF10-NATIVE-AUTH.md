## Transport and isolation

Only existing Linux GitHub CI can launch the adapter. Docker daemon is unavailable on the local Windows host; it must fail closed there. The same four immutable image identities as START-A are used (PG17, GoTrue, PostgREST14.17, Node22). Pulling is restricted to those digests; the historical private `dev07` PostgREST mirror is replaced only as a registry location by the official repository serving the **same digest**, otherwise setup stops. No mutable image/version fallback is permitted. Public registry availability must be confirmed by the actual CI run.

Reuse of the prior host-loopback Next fallback avoids installing/building a parallel image or dependency tree. The exact Git source is archived without env/private files; existing CI npm-ci modules must match its lockfile. The Next/SSR process receives only synthetic settings and a small platform environment allowlist. DB/Auth/REST are fresh ownership-labeled containers on an internal network, without host binds/published service ports; DB data is tmpfs. One separately attested ingress exposes only `127.0.0.1:32190`, and the application listens on `127.0.0.1:32189`. This host process is **not claimed to have zero default routes or enforced network egress isolation**. Requests made by the harness are destination-allowlisted; no product provider/model/market endpoints are invoked.

Only newly created `example.invalid` members A/B and admin are used. Bootstrap anon/service transport tokens have no member identity; member JWTs come from actual GoTrue password login, are verified through SDK `getUser`, and become real SSR cookies. PostgREST validates their signature and derives DB identity itself; no `set_config` actor fixture is used in acceptance requests. Local admin bootstrap is used only to create these disposable accounts; the app has no service-role key. Credentials/JWTs remain private temp files or request memory, never argv/log/Git/artifact uploads. Every POST intent is written privately before submission. Unknown outcomes stop; the deliberate response-loss probe independently GETs the receipt with a freshly authenticated session before one explicit exact retry.

The real run must attest identity/isolation, native accounts/getUser, actual reader-first UNAVAILABLE/writer closed before candidate SQL, minimum unchanged owner grants, real JWT lost-response/receipt/exact intent, two partial expenses (5000 declared), A/B independent writes and foreign/admin denial, bad JWT signature rejection, owner SELECT/service-role denial, and correction/history with unchanged fingerprints of all five existing financial/CF tables. All nine phases and ownership-checked cleanup are required for a PASS summary.

Candidate SQL applies only inside that fresh tmpfs DB. Existing financial and CF API calls create nonzero synthetic prerequisites once, then all PF10 actions must preserve those fingerprints. No grant-repair shortcut, new auth/provider setup, live account, primary SQL/env, main merge, service purchase or model/Hermes call is authorized. Real destination installation, backup/restore, production Auth/browser usability and Arash acceptance remain separate root gates. Execution is pending until exact-SHA CI/native logs substantiate it.

Auth verification follows official [getUser](https://supabase.com/docs/reference/javascript/auth-getuser) and [setSession](https://supabase.com/docs/reference/javascript/auth-setsession) contracts already supported by the installed SDK; no dependency upgrade is introduced.
