# انتشار کنترل سهمیهٔ مشترک BrsApi در لیارا

مالک اجرا: چت «تکمیل کارها و اتصال لیارا». مالک بازبینی: مدیریت پروژه. تاریخ: ۲۰۲۶-۱۰-۰۱. این بسته اصلاح و شاهد و دستور نصب است؛ وضعیت نصب از CI نتیجه‌گیری نمی‌شود.

گزارش تشخیصی داده و دستورکار مستقل توسعه: [پروندهٔ ممیزی](./market-data-audit-20261001/README.fa.md). منابع فنی بررسی‌شده: [Supabase Database Functions](https://supabase.com/docs/guides/database/functions)، [PostgreSQL 17 CREATE FUNCTION](https://www.postgresql.org/docs/17/sql-createfunction.html) و [changelog جاری Supabase](https://supabase.com/changelog). baseline/مرز روز از هیچ‌یک استنتاج نشده است.

## شاهد زنده، فقط‌خواندنی

دیتابیس مقصد PostgreSQL 17 روی VPS لیارا (`portfolio-stage-db-1`، دیتابیس `postgres`) است. رله برنامهٔ PaaS جداگانهٔ `arsadata` است؛ انتشار VPS رله را منتشر نمی‌کند.

در ۱ اکتبر، جدول `brsapi_budget_days` و دو RPC بودجه روی مقصد غایب بودند. نقش مالک `postgres` دارای BYPASSRLS و نقش‌های anon/authenticated/service_role موجودند. مجوز پیش‌فرض مقصد **اجرای تابع را به service_role می‌دهد**؛ نبود GRANT صریح در فایل قبلی به‌تنهایی شاهد خرابی مجوز این مقصد نیست. نسخهٔ اصلاحی گرنت‌ها را مستقل از پیش‌فرض‌ها صریح می‌کند.

`/debug` در `2026-10-01T09:18:32Z`: DB HTTP 200، دادهٔ رله ۲۴ ثانیه عمر، فاصلهٔ تنظیم‌شده ۱۰۰ms و کمینهٔ مشاهده‌شده ۱۰۹٫۱۳ms. **legacy enforcement=false، store unhealthy و RPC=PGRST202**. ۱۰۰ واحد اضطراری حافظه‌ای مصرف شده است. `used=0/remaining=9000` در همین پاسخ، باقی‌ماندهٔ واقعی نیست. `transport.sent=2506` شمارش از شروع فرایند است، نه مصرف تأییدشدهٔ روز نزد تأمین‌کننده.

باقیماندهٔ واقعی و مرز ریست سهمیهٔ تأمین‌کننده نامعلوم‌اند. هیچ fetch اختیاری تازه، ترمیم انبوه تاریخچه/NAV، تماس آزمایشی با BrsApi یا تغییر جدول مالی توسط این بسته انجام نشده است. تولیدکننده‌های موجود Production را متوقف/منتشر نکرده‌ایم؛ **کنترل زنده هنوز پذیرفته نیست**.

## اصلاح همان phase28

- جدول/شمارندهٔ موازی نداریم. `usage_verified` در همان جدول پیش‌فرض false دارد. روز غایب/نامعلوم با BRSB4 رد می‌شود؛ عبور از نیمه‌شب خودکار سهمیه نمی‌سازد. اپراتور باید baseline مصرف قبلی و پنجرهٔ واقعی تأمین‌کننده را تأیید کند.
- RPC lease با قفل ردیف، مجموع تخصیص‌ها را محدود می‌کند. کاهش سقف زیر مقدار تخصیص‌یافته، تخصیص جدید را متوقف می‌کند؛ مجوز قبلاً صادرشده را نمی‌توان پس گرفت. درخواست سقف بزرگ‌تر سقف ثبت‌شده را بالا نمی‌برد.
- release با امضای قدیمی no-op است. بدون شناسهٔ اجاره، retry پاسخ گمشده یا پس‌دادن تکراری می‌توانست ظرفیت باز کند. واحدهای استفاده‌نشده محافظه‌کارانه سوخته می‌مانند؛ هزینهٔ آن ظرفیت کمتر است.
- JS حتی با env قدیمی اضطراری، بدون lease مجوز نمی‌دهد. پاسخ نامعتبر RPC رد و فقط نام RPC، status و code خطا ثبت می‌شوند؛ message/details راه‌دور لاگ نمی‌شوند. باقی‌ماندهٔ نامعلوم null است؛ بعد از lease معتبر هم debug تخمین آخرین مشاهدهٔ آن فرایند است، نه حساب دقیق تأمین‌کننده.
- چرخهٔ متوقف‌شده پیش از نوشتن snapshot/history برمی‌گردد؛ حتی cold start دادهٔ سالم دیتابیس را با payload خالی جایگزین نمی‌کند. cold start بدون cache، `/market.json=503` می‌دهد. timestamp دادهٔ قدیمی تازه نمی‌شود. فرانت باید کهنگی را درست نشان دهد.

## آزمون و بازاجرا

PostgreSQL 17 در Docker اختصاصی، `--network none`، بدون پورت منتشرشده، دادهٔ مصنوعی و بدون credential واقعی. دو پروفایل مجوز: پیش‌فرض گستردهٔ مشابه مقصد و مجوزهای صریح بدون گرنت خودکار.

```powershell
docker run --name liara-budget-test-review --label codex.task=liara-budget-review --network none -e POSTGRES_HOST_AUTH_METHOD=trust -d postgres:17-alpine
$env:BRSAPI_BUDGET_TEST_ISOLATED='1'
$env:BRSAPI_BUDGET_TEST_CONTAINER='liara-budget-test-review'
node --test relay/brsapi-budget.integration.test.mjs
npm run test:relay
```

آزمون فقط دو دیتابیس مصنوعی `brsapi_guard_legacy_test` و `brsapi_guard_explicit_test` را می‌سازد/حذف می‌کند؛ کانتینر باید اختصاصی آزمون باشد. اجرای Docker خود دیتابیس را خاموش و روشن می‌کند. اتصال CI فقط به Postgres موقت loopback runner مجاز است؛ نبود opt-in خطاست و skip نمی‌شود.

| شاهد | نتیجه |
|---|---|
| PostgreSQL 17، چند مصرف‌کننده، baseline غیرصفر، restart، قطع/خاموش/روشن DB، کاهش سقف، release تکراری، گرنت و اجرای دوباره migration | PASS: ۱۴ تست، صفر fail/skip |
| خود server در child process با fetch mock، baseline نامعلوم | PASS: صفر upstream، صفر snapshot write، 503، lastRefresh=0، remaining=null |
| حساسیت همان آزمون با برگرداندن رفتار معیوب قبلی | FAIL مورد انتظار: یک write خالی و HTTP 200؛ بعد از بازگرداندن اصلاح PASS |
| کل test:relay، SQL validation، secret scan، lint و build محلی | PASS |
| نصب/پذیرش Production | BLOCKED / NOT DEPLOYED |

شاهد پاک‌سازی‌شدهٔ مقصد واقعی و محیط آزمون در [فایل metadata](./brsapi-budget-evidence-20261001.json) ثبت شده است. محیط آزمون PostgreSQL **17.11** بود. لاگ‌ها خارج Git در `reports/budget-guard-20261001/evidence` در workspace چت زیرساخت‌اند. آزمون CI بدون خاموش/روشن Docker اختصاصی ۱۳ تست دارد؛ ۱۴ مربوط به شاهد محلی است. آزمون EOD برای استخراج بدنه در Windows به LF نرمال شده تا CRLF نتیجه را خراب نکند.

مهارت‌های اعمال‌شده: Supabase برای بررسی مقصد/RPC، Supabase Postgres Best Practices برای قفل کوتاه و کمینهٔ مجوز، systematic-debugging برای تطبیق مرز رله → RPC → جدول واقعی، verification-before-completion برای خروجی تازه و شاهد حساسیت آزمون. خواندن مستندات رسمی تابع و changelog نیز انجام شد.

## نصب پس از بازبینی

1. SHA نهایی و CI همان نسخه بازبینی شوند. مصرف واقعی روز، مرز ریست، مالک کلید و تمام مصرف‌کنندگان آن مشخص شوند. مصرف مستقیم بیرون این شمارنده پوشش داده نمی‌شود. تا تعیین این موارد bulk شروع نشود؛ debug فعلی منبع baseline نیست.
2. مالک انتشار رله را موقتاً متوقف کند تا هیچ فرایند قدیمی/deployment هم‌پوشان در زمان تغییر شمارنده ارسال نکند. timestamp و آخرین snapshot فقط‌خواندنی ثبت شوند؛ وقفهٔ تازگی را اعلام کنید. financial UPDATE/DELETE/restore انجام نشود.
3. schema و ردیف‌های قبلی شمارنده، اگر موجود بودند، خصوصی بکاپ شوند. `sql/phase28_brsapi_budget.sql` روی **همان مقصد VPS** با مالک BYPASSRLS و `psql -X -v ON_ERROR_STOP=1 -f ...` اجرا شود؛ فایل تراکنش دارد. owner تابع، search_path، RLS و GRANTها بازخوانی شوند. هیچ روز یا lease آزمایشی در Production نسازید.
4. baseline فقط با شاهد معتبر اپراتور در همان جدول ثبت شود. leased کران محافظه‌کارانهٔ مصرف قبلی و تخصیص‌های جاری است و با حدس صفر نمی‌شود. baseline_note محل شاهد بدون کلید/رمز است. در صورت ابهام `usage_verified=false` و توقف رله حفظ شود؛ guard سهمیهٔ تازه نمی‌دهد.
5. پس از اعمال واقعی migration، `PHASE28_APPLIED` در workflow انتشار عادی صریحاً و با بازبینی true شود؛ اکنون عمداً false مانده است. guard + `BRSAPI_BUDGET_ENFORCE_LEGACY=1` + اضطراری صفر، پیش از شروع سرویس اعمال شوند. رله تک‌نمونه و کارهای اختیاری غیرفعال بمانند. rollout کلاینت مرکزی موضوع این بسته نیست.
6. سرویس یک‌نمونه‌ای شروع و فقط debug/health خوانده شود. DB سالم، baseline معتبر، enforcement=true و تخصیص ماندگار احراز شوند. refresh اجباری، درخواست تزریقی، `/market.json` برای آزمون، کلید دوم یا دورزدن گیت انتشار برای عبور از توقف بودجه انجام نشود.
7. مصرف طبیعی بعدی و حفظ snapshot در رد بودجه بررسی شود. هر روز جدید تا تأیید پنجره/مصرف قبلی نامعلوم است؛ سازوکار عملیاتی baseline روزانه باید پیش از rollout عادی تعیین شود. ترمیم تاریخچه/NAV فقط پس از این پذیرش و تعیین ظرفیت آغاز شود.

## rollback و اقدام باز

در خطا رله را متوقف و آخرین دادهٔ سالم را حفظ کنید. خاموش‌کردن enforcement، فعال‌کردن اضطراری، صفرکردن leased، حذف جدول یا بازگرداندن release کاهش‌دهنده، rollback امن نیستند. پیش‌فرض بازگشت: حفظ شمارنده/guard با سرویس متوقف. برگشت کد قدیمی فقط با حفظ منع ارسال و بررسی release انجام شود؛ timestamp دادهٔ قدیمی تازه نشود.

مانع دقیق: بازبینی نسخه، تعیین مصرف واقعی و پنجرهٔ روز تأمین‌کننده و نصب هماهنگ guard + migration + env. مجوزهای قبلی کاربر ادامهٔ اتصال لیارا را پوشش می‌دادند؛ دستور هماهنگی فعلی تحویل اصلاح/شاهد/دستور نصب برای بازبینی است. در این نوبت طرح جدید روی محیط مشترک نصب نشده است. اقدام آرش: شاهد سهمیه/مرز روز از پنل یا پشتیبانی BrsApi و هماهنگی بازبینی انتشار؛ هیچ کلید/رمزی در چت ارسال نشود.
