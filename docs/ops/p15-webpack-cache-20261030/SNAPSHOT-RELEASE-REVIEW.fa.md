# پاسخ اجرایی به بازبینی snapshot و مصرف رسید — ۳۱ اکتبر

بازخورد مشاور بررسی شد. نتیجه، **اثبات محدود بازیابی SQL** را نگه می‌دارد؛ آماده‌بودن انتشار از آن نتیجه نمی‌شود. کد پین‌شده و فایل‌های موجود سرور فقط‌خواندنی بازخوانی شدند؛ backup، SQL، شروع کپی یا retry تازه‌ای انجام نشد.

## dump و inventory هسته از کدام snapshot آمده‌اند؟

در [helper اجراشده](../recovery-01/p01-scripts/liara-native-backup-restore.py)، خطوط۱۶۷–۱۸۷، یک نشست `REPEATABLE READ READ ONLY`، `pg_export_snapshot()` می‌گیرد و باز می‌ماند. همان متغیر `snapshot` هم در `SET TRANSACTION SNAPSHOT` برای تمام INVENTORY هسته و هم در آرگومان `pg_dump --snapshot` مصرف می‌شود. خروج هر فرمان بررسی می‌شود؛ نشست صادرکننده پس از dump/globals/cron بسته می‌شود. SHA256 همان helper روی سرور همچنان `1f1454f9aea632609c002335e628c2f463f96f28cb131bc95c2ff6f2bda2a9f2` است.

بازخوانی در۳۱اکتبر۰۲:۴۴:۲۳تهران ثبت کرد: فهرست هسته در۲۱:۵۳:۱۱Z و dump در۲۱:۵۴:۱۷Z نوشته شده‌اند؛ این ترتیب **به‌تنهایی** اثبات snapshot نیست، شاهد اصلی اتصال هر دو فرمان به همان snapshot در کد اجراشده است. شناسهٔ snapshot در receipt اصلی ذخیره نشده؛ event مستقل حاوی شناسه/هر دو فرمان نداریم و از گذشته نمی‌سازیم. مقایسه نهایی هدف با همان فایل هسته۲۰۸۴خطی هیچ استثنایی ندارد. رشد دو شمارندهٔ مبدأ زنده فقط guard بعدی را توضیح می‌دهد و جای این سازوکار را نمی‌گیرد.

**حدود مهم:** فهرست مکمل سه schema/۱۹function در wrapper، پیش از helper با تراکنش جدا خوانده شده است. برابرشدن آن با هدف و مبدأ در اصلاح بعدی، مشاهدهٔ سازگاری است؛ آن را به‌عنوان inventory گرفته‌شده از همان exported snapshot معرفی نمی‌کنیم. `pg_dumpall --globals-only` نیز آرگومان snapshot مشترک ندارد. این گزارش سازگاری اتمی تمام نقش‌ها/مجوزهای سراسری/metadata مکمل را ثابت نمی‌کند. اگر نسخه انتشار به چنین اثباتی وابسته شود، root پیش از اقدام آن گیت را جدا می‌بندد؛ dump قدیمی برای تولید شاهد تازه تکرار نمی‌شود.

## رسیدی که ابزار انتشار باید مصرف کند

[binding نسخه‌دار](RELEASE-BINDING-20261031.json) وضعیت `NOT_READY_FOR_RELEASE_CONSUMPTION` دارد. اصل receipt همچنان failed با hash `b3cc167b604740207f884db3b037fea59e976fe296a72ed51527d79133d40aef` است؛ رسید تصحیح مستقل با hash `e4a794edff3bd2b626d41feb8f8ec5a520683b4b76b66bd6bad63cee18cccde9` پذیرفته شده است. نه status اصلی تغییر می‌کند و نه صرف نادیده‌گرفتن failed معتبر است.

دو مصرف‌کننده موجود بررسی شدند: `scripts/ops/cashflow-checkpoint/backup-checkpoint.ps1` فقط proof با status=passed و همان هفت فایل قدیمی را قبول می‌کند؛ `scripts/testing/consultation/install-native.py` نیز به checkpoint قدیمی `20261023T204308Z` و receipt passed آن مقید است. بنابراین **هیچ‌کدام اکنون مصرف‌کننده آمادهٔ رسید تصحیح جدید نیستند**. فایل منجمد یا guard آن‌ها برای عبور این checkpoint تغییر نکرده است. نصب و Capture با این مسیر قدیمی انجام نمی‌شود.

اقدام root پیش از نصب: تهیه و بازبینی تغییر مشخص همان مسیر مصرف، با پین checkpoint/source/target/dump/helper و hash رسید اصلی+تصحیح+مقایسه‌ها؛ بازخوانی سالم/توقف/isolation در زمان استفاده؛ بررسی hash کامل dump در همان گیت، نه اتکا به stat امروز. اختلاف یا intent نامعلوم فقط readback و توقف، هرگز retry خودکار helper نیست. بازخوانی امروز برای کاهش بار فقط اندازه/زمان dump را خوانده و hash قبلاً ثبت‌شده آن را نقل می‌کند؛ hash مجدد۲٫۴GB ادعا نشده است.

## Storage و کپی دارای داده واقعی

SQL شامل metadata مربوط به Storage است و پشتیبان فایل‌ها نیست. اگر مسیر انتشار فایل/attachment را جابه‌جا کند، قبل cutover باید manifest/hash/restore فایل‌ها بسته شود؛ نبود وابستگی فایل نیز باید از consumer واقعی مستند شود. تا آن تعیین، گیت باز است.

بازخوانی تازه: مبدأ همانID/image و healthy؛ کپی همانID، متوقف، network=none، بدون پورت، فرمان cron=off. `health=unhealthy` ثبت Docker برای کپی متوقف، سلامت برنامه یا قابل ورود بودن محسوب نمی‌شود. کپی عمومی، محیط عضو یا منبع دادهٔ آموزشی نخواهد شد. A/B/C مستقل ادامه می‌دهند؛ این بازبینی هیچ آماده‌استفاده‌بودن مقصد، ادغام Liara، نصب Hermes یا انتشار اصلی را تأیید نمی‌کند.
