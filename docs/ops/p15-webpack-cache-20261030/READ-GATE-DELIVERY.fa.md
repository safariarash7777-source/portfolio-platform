# مصرف واقعی رسید اصلاح‌شده؛ گیت فقط‌خواندنی

در۳۱اکتبر۰۳:۱۸:۰۵تهران، [اعتبارسنج نسخه‌دار](checkpoint-read-gate.py) با کد دقیق و binding پین‌شده، در حافظه روی Linux موجود اجرا شد و [رسید واقعی](../../plan/development-v04-20261029/evidence/P15-checkpoint-read-gate-root-20261031.json) `PASS_PINNED_SQL_RESTORE_READ_GATE` داد. این اجرای کدِ خواندن و تطبیق چند رسید است؛ صرف تأیید یک hash یا تغییر متن برنامه نیست. **Capture و installer قبلی هنوز این رابط را فراخوانی نمی‌کنند؛ مجوز نصب یا انتشار ایجاد نشده است.**

## چه چیزی بررسی شد؟

- قفل اشتراکی غیرمسدودکنندهٔ همان release، هویت واقعی مبدأ و کپی، توقف کپی، network=none/بدون پورت، مالکیت، cron=off و عدم اشتراک mount با مبدأ؛ پیش و پس از خواندن فایل بزرگ.
- اصل receipt با وضعیت failed، intent/plan/result تصحیح، comparison کامل۲۰۸۴خطی و سهschema/۱۹function؛ هم hash دقیق بایت‌ها و هم ارتباط معنایی checkpoint/dump/هویت/اصلreceipt در آن‌ها. failed به passed تغییر داده نشده و استثنای شمارندهٔ زنده به مقایسهٔ هدف راه ندارد.
- اصل نتیجهٔ wrapper شکست‌خورده و فهرست خصوصی مکمل، helper همان نسخه و بدون جایگزینی؛ مسیرها ثابت و allowlist، فایل‌ها/پوشه‌ها root-owned و بدون symlink/نوشتن مشترک، اندازهٔ فایل کوچک محدود است.
- **تمام۲٬۴۰۶٬۵۴۶٬۲۹۵بایت dump دوباره روی خود سرور خوانده شد** و SHA256 همان `87434f8c53cca9910cdbd953415ffed5e01d3aacb0db8c0702a4e164253c8c17` به دست آمد. اندازه/inode/زمان فایل حین خواندن ثابت و فایل‌های کوچک پس از آن دوباره یکسان بودند. این بار hash تازه است؛ محدودیت stat-only گزارش قبلی به این رسید منتقل نمی‌شود.

هیچ SQL، dump/restore دوباره، شروع/توقف container، انتقال فایل پشتیبان، نصب، منبع یا هزینه تازه‌ای انجام نشد. کد با nice۱۹ و بافر۱MiB برای dump اجرا شد؛ این حد بافر است، نه ادعای سقف سخت CPU/RAM کل سیستم. فایل کد روی سرور نوشته نشد و دادهٔ پایگاه به لپ‌تاپ نیامد؛ فقط رسید تصفیه‌شده برگشت.

## نسخه و آزمون قابل بازتولید

[آزمون‌های مرزی](test_checkpoint_read_gate.py) بدون Docker/SSH/SQL، با receiptها و حالت‌های آموزشی اجرا می‌شوند:

```text
python -B docs/ops/p15-webpack-cache-20261030/test_checkpoint_read_gate.py
```

۱۷آزمون روی Windows و همان۱۷ روی Linux موفق‌اند: جابه‌جایی checkpoint/source/target/dump، حذف/افزودن فایل، دستکاری بایت و ارتباطreceipt، بازبرچسب‌زدن failed، ورود استثنای rowcount به core، تغییر plan/private inventory، آنلاین/روشن‌شدن کپی، mount مشترک/قابل‌نوشتن، مبدأ ناسالم، مسیر خارج allowlist و بازپین‌کردن binding رد می‌شوند.

اولین import آفلاین رویWindows پیش از اجرای هر تست به‌علت fcntl شکست خورد؛ import مخصوصLinux به run منتقل شد. پس از آن۱۶آزمون موفق و با افزودن guard بازپین‌کردن binding،۱۷آزمون موفق شدند. اجرای Linux نهایی همان نسخهٔ۱۷تایی است؛ شکست اولیه حذف یا موفق نامیده نمی‌شود.

binding دقیق `7819e0fb16bbb2c9171099cab07953c3137634d665616af509d4061306af9325` است؛ gate اجراشده SHA256=`9289f162919bd1b2e462d2c823758b7b693f27988562d3554be197c9b65666a3` و تست اجراشده SHA256=`19e22156c46dc985240ea7412763609ad6af6dca80fc8a6d4e9c3510eaf6d4c7`، بر مبنای بایتLFواقعاً اجراشده. ورودی زنده فقط همینbindingمستقلِ بازبینی‌شده است؛ fixture بازپین‌شده فقط تابع خالص را می‌سنجد و از entrypoint زنده عبور نمی‌کند. اجرای مستقیم فایل بدون launcher بازبینی‌شده هیچ عملیاتی انجام نمی‌دهد.

## محدودیت و اقدام بعدی root

این گیت **وضعیت فعلی schema/دادهٔ SQL یا ظرفیت تازه را نخوانده**؛ سلامت container و صحت آرشیو/شواهد همان checkpoint را می‌سنجد. metadata مکمل خصوصی و globals از exported snapshot مشترک هسته گرفته نشده‌اند؛ این حد همچنان محفوظ است. پشتیبان Storage binary، بسته ساخت متصل، reader واقعاً مستقر و پذیرش عضو جدا هستند.

اقدام بعدی، اتصال صریح همین attestation و فایل‌های مکمل به نسخه مشخص ابزار Capture/Verify و installer موجود با حفظ پشتیبانی آرشیوهای قبلی است؛ آن اتصال هنوز انجام نشده و binding تاریخی تغییر نمی‌کند. گرفتن نتیجه این گیت، حق خودکار retry backup یا نصب نمی‌دهد. اصل crypto/helper و receiptهای قبلی دست‌نخورده‌اند؛ کار محصول A/B/C مستقل ادامه دارد.
