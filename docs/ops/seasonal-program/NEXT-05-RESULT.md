## قرارداد04 و وابستگی ادغام

`CourseCatalog` فقط `GET /api/courses` با `contractVersion: seasonal.v0.1` را مصرف می‌کند. ردیف واقعی published، timezone تهران، `startsAt/endsAtExclusive: null|string` و registrationAction غیرفعال اعتبارسنجی می‌شوند. تاریخ null «هنوز اعلام نشده» است؛ هیچ آغاز/پایان یا partner فرض نمی‌شود. `registrationAction.enabled=false` همراه دلیل به دکمهٔ غیرفعال تبدیل می‌شود. وضعیت HTTP یا payload نامعتبر، پیام «اطلاعات دوره دریافت نشد» و retry می‌دهد؛ پاسخ معتبر `courses:[]` حالت خالی جدا دارد.

API04 در checkout مستقل05 وجود ندارد؛ مشاهدهٔ مستقل05 در این مسیر 404 و خطای صادق بوده است. حالت واقعیِ پاسخ خالی با interception مرورگر فقط در محیط آزمون دیده شد. پس از تجمیع04 و05 باید smoke دریافت actual published rows دوباره انجام شود. این وابستگی، fallback دادهٔ نمونه به محصول ایجاد نکرده است.

فهرست وبینار قدیمی از endpoint موجود استفاده می‌کند؛ تاریخ‌ها با timezone تهران نمایش داده می‌شوند، `platform_url` عمومی رندر نمی‌شود و query callback `status=success` پرداخت/عضویت را تأیید نمی‌کند. ثبت‌نام و ساخت پرداخت موجود حفظ شده‌اند؛ عضویت فصلی جدید از این UI ساخته نمی‌شود.

## درخواست وقت و پیگیری

`POST /api/waitlist` با payload ثابت `{email}` حفظ شده است. فقط receipt JSON صریح `{success:true}` ارسال موفق را تأیید می‌کند. پاسخ409، 429، 500، JSON نامعتبر و قطع شبکه موفقیت تلقی نمی‌شوند؛ متن راهنما و ورودی حفظ می‌شود. خطای سرویس داخلی به کاربر افشا نمی‌شود. ایمیل پس از موفقیت پاک و فرم با پیام دریافت درخواست غیرفعال می‌شود؛ receipt رزرو وقت نیست.

وضعیت‌های درخواست: ورود اطلاعات → در حال ارسال → دریافت درخواست / خطای قابل اصلاح. پیگیری فعلی از راه تماس با همان ایمیل است؛ کاربر دارای حساب به `/dashboard/consultation` هدایت می‌شود. هیچ ادعای نمایش درخواست جدید در پنل یا پروندهٔ online ساخته نشده است؛ پیوند lead جدید به پرونده/پیگیری NEXT08 نیازمند backend متناظر است. این محدودیت در متن صفحه روشن است.
