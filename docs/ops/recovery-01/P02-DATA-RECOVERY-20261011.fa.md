## خطاهای قطعی خوانندهٔ کدال و اصلاح آماده

۱. API منتشرشده `/api/codal-list?symbol=داریوش بازار` در 09:11 UTC، HTTP 200 و `data: []` برگرداند. همان نماد در `codal_feed` ردیف واقعی دارد و خواندن anon آن هم HTTP 200 است. علت در کد منتشرشده مشخص است: API فقط `codal_reports`، یعنی گزارش‌های مالی پردازش‌شده، را می‌خواند ولی UI آن را «همهٔ اطلاعیه‌ها» معرفی می‌کند. مجمع، شفاف‌سازی و سایر اطلاعیه‌ها لزوماً در جدول parser نیستند.

۲. صفحهٔ `/codal` با `id.desc` قبل از limit مرتب می‌شود. شاهد امروز: id بالاتر `12273` ساعت ارسال `۰۸:۱۱:۵۴` دارد، اما `12240` ساعت `۱۱:۰۴:۳۷`. ترتیب درج، ترتیب منبع نیست. گزارش‌های پردازش‌شده هم tail جدیدِ بک‌فیل سال ۱۴۰۱ دارند؛ از آخرین id نمی‌توان «نبود گزارش تازه» را نتیجه گرفت.

۳. API قبلی در نبود `raw.date_publish` از `period_end_jalali` استفاده می‌کرد. علاوه بر آن، prop موسوم به `jdate` در تب گزارش‌ها از `data.period_end` پر می‌شد ولی نوع آن «تاریخ انتشار» نوشته شده بود. دورهٔ گزارش، انتشار منبع، ارسال اطلاعیه و دریافت سیستم چهار مفهوم متفاوت‌اند.

۴. صفحهٔ feed تمام خطاهای SDK را «فید هنوز راه‌اندازی نشده» معرفی می‌کرد؛ خطای مجوز، ستون، شبکه یا schema cache نبود داده را ثابت نمی‌کند.

اصلاح commit cf00f16 اکنون آماده است:

- `/api/codal-list` فقط metadata جدول `codal_feed` را می‌خواند؛ دادهٔ مالی سنگین `raw/data` یا رله را نمی‌خواند. پوشش پاسخ صریحاً `stored-announcements` است.
- sort تاریخ و ساعت ارسال قبل از id و limit اعمال می‌شود؛ ساعت غایب null می‌ماند. `dateKind=sent` و زمان ارسال جدا برمی‌گردند. زمان دورهٔ مالی fallback زمان ارسال/انتشار نیست.
- صفحهٔ `/codal` نیز تاریخ و ساعت ارسال را مقدم می‌گیرد و خطای خواندن را از مسیر جدولِ در دسترس نبودن جدا می‌کند؛ هیچ‌کدام به‌خودی‌خود ادعای «نصب نشده» ندارد.
- UI تب نماد «اطلاعیه‌های ذخیره‌شده» و «دورهٔ مالی» را درست نام می‌برد؛ تاریخ‌ها رقم فارسی دارند.

ترتیب سمت DB بر قالب تاریخ فعلی feed تکیه دارد؛ نمونه‌های امروز تاریخ جلالی ثابت با رقم فارسی داشتند. پیش از مهاجرت به قالب‌های مخلوط یا ناقص، باید ساعت منبع در producer به قرارداد canonical تبدیل شود. این تحویل چنین migration یا تغییری در provider انجام نمی‌دهد.

بازپخش آفلاین با نمونهٔ واقعاً دریافت‌شده، از همان تابع route اصلاح‌شده برای داریوش بازار یک اطلاعیه گرفت؛ این شاهد اصلاح کد است و پذیرش production نیست. بازپخش actual `toMarket`، `withValidNav` و `OptionsBoard` نیز علت missing-time / unknown-unit را روی دادهٔ تازه روشن کرد. receipt غایب در projection نمونه از `updated_at` جعل نشد و null ماند.

## حدود دسترسی و آنچه هنوز معلوم نیست

خواندن‌های کوچک دیتابیس و API اصلی موفق بودند، ولی پاسخ کامل snapshot و چند آرایهٔ بزرگ پس از HTTP 200 هنگام دریافت body timeout دادند. `Connection: close` مشکل را به‌صورت عمومی حل نکرد. بنابراین این خطا را «جدول خالی»، «تمام سرور قطع» یا «علت قطعی شکست Vercel» نمی‌نامیم. DB reader منتشرشده deadline حدود ۵ ثانیه دارد؛ اندازهٔ پاسخ و مسیر Vercel→DB باید در همان runtime سنجیده شود. پاسخ کوچک موفق، سلامت دریافت payload کامل را اثبات نمی‌کند.

SSH با کلید موجود، BatchMode و StrictHostKeyChecking روی مسیر مستقیم و proxy محلی موجود timeout داد. عبور HTTP CONNECT به‌تنهایی موفقیت SSH نیست. API تازهٔ config/release لیارا نیز نتیجهٔ کامل قابل‌استفاده نداد. مرورگر داخلی در navigation/state timeout داد و پذیرش DOM تازه برای سهام/صندوق/اختیار یا مدیر FX حاصل نشد. هیچ بررسی ورود مجدد مالک، logout، bypass TLS یا تغییر تنظیم شبکه انجام نشد.

`brsapi_budget_days` از REST امروز HTTP 404 / `PGRST205` داد. این «مسیر جدول در schema cache در دسترس نیست» است؛ بدون catalog مستقیم، ادعای حذف قطعی جدول یا نتیجه‌گیری دربارهٔ RPCها نمی‌کنیم. هیچ فراخوانی رزرو بودجه انجام نشد. مصرف واقعی کل key، مصرف همهٔ سرویس‌ها و IPها، replica واقعی، طرح خریداری‌شده، پنجرهٔ reset و headroom همگی UNKNOWN هستند. شمارندهٔ فرایند یا configured scale=1 جای آن‌ها نیست.

[قوانین رسمی BrsApi](https://brsapi.ir/tsetmc-exchange-free-bourse-api-key-request/) برای دسترسی معمول ۳۰۰ درخواست در ۵ دقیقه با فاصلهٔ ۳۰۰ms و برای AIO، ۲۰۰۰ درخواست در ۵ دقیقه با فاصلهٔ ۵۰ms بیان می‌کند؛ محدودیت IP مستقل نیز ذکر شده است. این صفحه طرح فعال این key یا مصرف واقعی حساب را مشخص نمی‌کند. صرف پیام سابق تأمین‌کننده یا فاصلهٔ یک فرایند، مجوز افزایش job، restart یا خرید هاست تازه نیست.

برای انتقال تاریخی، شواهد امروز وجود snapshot، feed، reports و history را تأیید می‌کنند؛ شمارش دقیق هر جدول/روز/نماد، دوره‌های جاافتاده، checksum نسخهٔ مبدأ و مقصد و کامل‌بودن فایل‌های ذخیره‌سازی هنوز تطبیق نشده‌اند. گزارش قدیمی restore به‌تنهایی آن پذیرش جامع را ایجاد نمی‌کند. هیچ مقدار گمشده صفر و هیچ دوره‌ای با حدس پر نشده است.

Rollback اصلاح وب: برگشت همان delta کدال روی candidate منتشرشده با نگه‌داشتن اصلاحات مستقل عضو؛ deploy یک آرشیو قدیمی به‌صورت کلی مجاز نیست. این patch هیچ schema، جدول، سطر، نگهبان نقش یا کلید عملیاتی را تغییر نمی‌دهد؛ rollback آن نیاز به حذف داده ندارد. نصب رله در این تحویل انجام نشده و receipt نصب/backup تازه یا rollback عملیاتی برای آن ادعا نمی‌شود.

## آزمون و بستهٔ شاهد

۵ آزمون تازهٔ route/خطا/رندر، ۱۳۶۰ آزمون core و ۱۰۶ آزمون calc موفق شدند؛ typecheck و lint موفق، build تولیدی کامل شد. متن نهایی پیام خطا پس از build محلی روشن‌تر شد؛ build/CI نهایی باید روی HEAD نهایی همین تحویل بررسی شود. آزمون‌ها روی DB عملیاتی اجرا نشده‌اند. اسکن staged نخست برای ۱۰ فایل کد، بدون یافته بود؛ رسید نهایی CI و SHA تحویل جدا ثبت می‌شود و بدون نتیجهٔ آن، CI سبز نهایی ادعا نمی‌شود.

شواهد غیرمحرمانه در `docs/ops/recovery-01/evidence-p02-20261011/` ذخیره شده‌اند: alias و اتصال، ساعت‌های طبیعی snapshot، نمونهٔ هر family، tail در برابر ترتیب منبع کدال، پاسخ API production، خواندن anon، unit metadata parser، history، quota schema، FX health، خطاهای دسترسی و actual-consumer offline. فایل‌های خام مالی و پیکربندی دارای credential فقط در محل خصوصی باقی مانده‌اند و داخل بسته نیستند. `scripts/ops/p02-live-family-proof.ts` بازپخش قطعی و بدون شبکهٔ همین نمونه‌ها را اجرا می‌کند.

نتیجهٔ قابل تحویل: DB فعلی زنده و دارای داده است؛ ایراد مشخص خوانندهٔ کدال اصلاح و آزموده شده، ولی هنوز منتشر نشده است. تازگی کامل بازار، نصب همسان رله، کامل‌بودن مهاجرت و پذیرش واقعی همهٔ صفحات باز می‌مانند. موفقیت این patch نباید به‌عنوان «حل کامل دریافت داده» گزارش شود.
