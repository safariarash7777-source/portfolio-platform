# START-A — مشخصات پذیرش مالی تا مشاوره، نسخه ۰٫۴

مأموریت ۲۹ اکتبر ۲۰۲۶: اجرای مسیر موجود با داده ساختگیِ صریح و تحویل نقص اصلاح‌شده یا رسید رفتار درست. مرجع وضعیت مشترک نزد هماهنگ‌کننده است؛ این سند فقط قرارداد همین برش است.

## نسخه و بازاستفاده

- استفاده از `/dashboard/cashflow`، `/dashboard/goals`، `/dashboard/consultation`، `/admin/consultation`، API/قراردادهای `lib/consultation` و `sql/consultation_workflow.sql`. roster و پاسخ نسخه‌دار موجود دوباره ساخته نمی‌شوند.

## رفتار و شرط پایان

1. دو نسخه مالی و reload مستقل، نسخه‌های قبلی و مبنای استفاده‌شده را حفظ کنند.
2. رضایت، درخواست، پیش‌نویس، تأیید نسخه مشخص و انتشار، مرحله‌های مجزا باشند. تغییر مبنای مالی/پژوهش، مجوز انتشار با تأیید قدیمی ایجاد نکند.
3. عضو B و مشاور نامرتبط به پرونده A دسترسی نگیرند؛ لغو رضایت، خواندن/نوشتن بعدی غیرمجاز را ببندد و تاریخچه را حذف نکند.
4. خطای read با پرونده خالی یکی نشود؛ شکست save و نتیجه نامعلوم، متن/هویت همان intent را حفظ کند. نتیجه نامعلوم ابتدا مستقل بازخوانی شود.
5. پیگیری و سؤال/پاسخ مرتبط، موجودی را خودکار تغییر ندهند. وضعیت‌های «بخشی/نکردم» با enum فعلی مقایسه و شکاف ثبت شود؛ تغییر قرارداد مشترک ضمنی نیست.
6. نقش، رضایت و حق خرید مستقل‌اند؛ نبود اتصال حق خرید فقط عرضه پولی را مسدود کند. آزمون داخلی می‌تواند مستقل ادامه یابد.

## حدود

مالک کد: این چت، consultation و جریان مالی مرتبط. قرارداد مشترک/migration تک‌مالک و نیازمند تطبیق مصرف‌کننده‌هاست. فایل‌های COMMAND-CENTER/README/BLUEPRINT/DECISION-LOG و package مشترک ویرایش نمی‌شوند. حساب، تأیید، ارسال به عضو، مدل و تغییر تولید واقعی اجرا نمی‌شود؛ تغییر ظاهر فقط در پیش‌نمایش. شاهد mock، SQL ایزوله، مرورگر و Production جدا ثبت می‌شوند.

## قرارداد افزودهٔ پیگیری — واگذاری هماهنگ‌کننده، ۲۹ اکتبر

هماهنگ‌کننده اجرای همین شکاف را به این مالک واگذار کرد؛ انتخاب قبلی مالک تکرار پرسش نمی‌شود. نام فنی `partial` برای «بخشی انجام دادم» و `not_done` برای «انجام ندادم» است. هر دو به actionKey معین و مسئول همان اقدام متصل‌اند؛ جزئیات متنی غیرخالی حداکثر ۲۰۰۰ نویسه لازم است. پنج مقدار قدیمی و معنایشان تغییر نمی‌کنند؛ سؤال عضو همچنان `question` و پاسخ مشاور قرارداد مستقل قبلی است.

CAS/baseVersion و clientToken موجود، تاریخچه append-only، شناسه نسخه جمع‌بندی و مسئول اقدام حفظ می‌شوند. هیچ جدول مالی/موجودی در مسیر این پیگیری نوشته نمی‌شود. SQL candidate فقط قید وضعیت و دو kernel خصوصی لازم را توسعه می‌دهد؛ wrapper عمومی، مالک/ACL/RLS و سایر مراحل گردش تغییر نمی‌کنند. پیش‌نیاز دقیق و امتناع از بازگشت ناسازگار پس از ثبت وضعیت تازه آزموده می‌شود؛ نصب production مجاز نیست.

تحویل به لپ‌تاپ وابسته نیست: PR نسخه‌دار روی کد موجود و Preview آنلاین موجود لازم است. fixture فقط داده برچسب‌دار مصنوعی دارد و صفحه‌اش در production غیرفعال است؛ هیچ auth/حساب واقعی یا فراخوانی مدل لازم نیست.
