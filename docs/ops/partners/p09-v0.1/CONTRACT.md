# P09 — قرارداد پیشنهادی `partner-report.v0.1`

این قرارداد فنی پیش‌نویس است؛ قرارداد تجاری یا API رسمی شریک نیست. تنها نمونه آفلاین با داده ساختگی اجرا می‌شود. مالک این مسیر P09 است؛ auth، schema، holdings، publication، package scripts و سه سند مشترک در مالکیت مجریان فعلی می‌مانند.

## مرز و بازاستفاده

مبنای checkout: PR195@31c44ab635b672b589b7833bcbc78b41d36f1e75، شامل PR191@a83f71d. PR175/184 ورودی/مجوز دوره را دارند؛ رسید ثبت‌نام دوره، گزارش ثبت‌نام کارگزاری نیست. UUID هویت موجود مصرف می‌شود و هیچ حساب، مجوز، دارایی یا انتشار دیگری ساخته نمی‌شود. رضایت مشاور و اعلان تلگرام رضایت اشتراک اطلاعات با شریک نیستند. فایل اصلی گزارش باید در ذخیره‌ساز محدود موجود، با hash، منبع، زمان دریافت و دسترسی ممیزی‌شده نگهداری شود؛ این نمونه فایل خصوصی ذخیره نمی‌کند.

## ورودی adapter، بدون endpoint نصب‌شده

`preview(report, acceptedEvents)` خروجی ردیف‌های قابل قبول، تکراری، اختلاف و رد را می‌دهد. `apply` فقط در نمونه حافظه‌ای با append اجرا می‌شود؛ endpoint HTTP، DB schema و انتقال داده ندارد. عملیات آینده نیازمند P01، قرارداد واقعی، رضایت دارای دامنه، مجوز سرور، preview تأییدشده و transaction/قید یکتایی در ذخیره‌ساز مشترک است. dry-run ساختگی جای این پذیرش نیست.

هر رخداد فیلدهای زیر را دارد (فایل `example.json` نمونه اجرایی است):

| فیلد | معنا |
|---|---|
| schema_version | دقیقاً partner-report.v0.1 |
| partner_id / contract_id / contract_version / offer_id | مرجع نسخه تغییرناپذیر قرارداد و شرایط؛ قرارداد واقعی نامعلوم |
| source_event_id / source_revision | یکتایی منبع در محدوده partner؛ تکرار یک نسخه با محتوای متفاوت اختلاف است |
| referral_ids / member_ref / consent_ref / external_subject_ref | صفر/یک/چند کد، UUID هویت موجود در عملیات آینده، مرجع رضایت مجاز و شناسه بیرونی اختیاری؛ داده خصوصی خام ممنوع |
| event_type | conditions_viewed, referral_clicked, registration_reported, partner_confirmed, activity_reported, commission_reported, invoice_reported, receipt_reported |
| occurred_at / received_at | ISO با offset؛ زمان دریافت از سامانه، مستقل از زمان وقوع |
| period / source_ref / source_hash | دوره صریح، مرجع گزارش محدود و SHA256 اصل فایل؛ hash به‌تنهایی اصالت منبع نیست |
| amount / unit / fee_basis_ref | مقدار صحیح به صورت رشته یا null؛ IRR یا IRT، بدون تبدیل حدسی؛ مبنای کارمزد فقط ارجاع به بند قرارداد |
| verification | reported یا verified؛ در نمونه همه reported؛ verified در عملیات فقط با تأیید مجاز و شاهد |
| corrects_event_id | اصلاح append-only دقیقاً آخرین نسخه همان source_event_id؛ اولین نسخه null |

شناسه داخلی نمونه با `fixture:` مشخص می‌شود و UUID واقعی نیست. schema_version با contract_version فرق دارد. در اصلاح منبع، نسخه قرارداد قبلی حفظ می‌شود؛ قرارداد جدید باید مرجع رویداد تازه داشته باشد و گذشته را بازنویسی نکند. از زمان received_at نسخه قرارداد حدس زده نمی‌شود. تعدد کد معرفی یا نبود رضایت/انتساب، صف بررسی می‌سازد؛ هیچ قاعده first/last-touch قطعی انتخاب نشده است.

کلیک، ثبت‌نام، فعالیت، کارمزد، صورتحساب و وصول رخدادهای مستقل‌اند. هیچ گذار خودکار بین آن‌ها نیست. مقدار نامعلوم null می‌ماند. مبلغ ساختگی در fixture صرفاً «مبلغ گزارش‌شده» است؛ نرخ، AUM، کارمزد محاسبه‌شده و وصول تأییدشده همه null هستند. اختلاف مبلغ فقط بین مبلغ گزارش‌شده کارمزد و صورتحساب هم‌واحد، هم‌قرارداد و هم‌دوره مقایسه می‌شود؛ برابری مبلغ به معنای تأیید/وصول نیست. برای قرارداد جدید در میانه دوره گروه مقایسه جدا باقی می‌ماند.

## گیت عملیات و بازگشت

تا P00 مبنا/مالکیت مشترک را نهایی نکند و P01 و قرارداد/گزارش واقعی پذیرفته نشوند، نمونه به مسیر عضو نصب نشود. حداقل یک دوره واقعی با شاهد ثبت‌نام، ردیف بی‌انتساب، گزارش اصلاحی، صورت‌حساب و وصول با عملیات تطبیق شود. مزیت عضو و سهم کسب‌وکار جدا تأیید شوند. اصل فایل و تاریخچه حذف نشوند؛ کلید توقف import، خروجی preview و رسید commit با فهرست شناسه‌ها لازم‌اند. بازگشت این تحویل فقط حذف مسیر نمونه از شاخه است؛ هیچ migration یا داده‌ای نصب نشده است.
